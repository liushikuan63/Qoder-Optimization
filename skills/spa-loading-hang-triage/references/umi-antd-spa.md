# umi-request / antd SPA 加载卡死参考

## 实测坑（历史现场）

- 网关 `HTTP 203` 是常态，不是鉴权失败；曾把它当 401 处理导致误跳登录，后回退。
- `umi-request` 的 `errorHandler` 返回 `undefined` 会把超时/reject 变成 resolve，页面误显示「无数据」；必须 `throw` 或返回 rejected Promise。
- 主包 404 时 `global.tsx` 来不及执行，`global.tsx` 里的看门狗不会生效；兜底必须内联进 `index.html`。
- 双入口（主应用/子应用）都要 `Cache-Control: no-store`；只改一个会出现「刷新好、从门户进卡」。
- 增量部署要保留旧 chunk 至少一个发布周期，否则已打开页面路由切换会 404。
- 启动兜底浮层在浅色背景下要保证对比度；不要用低对比度灰字。
- 轮询请求在组件卸载/路由切换时清理，避免叠加。

## 建议参数（按现场调整）

- 请求超时：30s。
- 首屏兜底：15s 显示重试。
- 分包重试：一次自动重试 + 可见重试浮层。
- 入口缓存：`Cache-Control: no-store`（主入口与子入口）。

## 故障注入矩阵

1. 主包 404。
2. 瞬时分包 404（第一次失败，第二次成功）。
3. 持续分包 404。
4. 接口悬挂（不返回）。
5. HTTP 203。

每类都用真实浏览器验证：页面可见状态、console、network、是否跳登录、loading 是否复位。

## 验收注意

- 等待判据：网络静默 + 关键 DOM/行数断言；不要用「等空表」「等 svg」。
- 静态截图可用 `headless-spa-screenshot` 的延迟 load 方法；交互与登录态验收用真实浏览器。
- 部署后从真实入口复验，确认加载新版本；不要只在开发环境验证。
