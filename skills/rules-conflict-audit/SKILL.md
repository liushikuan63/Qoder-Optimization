# 规则体系冲突审计

六维交叉比对规则体系，找出语义级冲突与口径漂移，产出可执行的编辑建议。

## 适用场景

- 合并外部包后的规则体检（`merge-inbound-qoder-package` 末尾「审阅 AGENTS 与技能」的深化版）
- 规则大改前的冲突排查（新增 hook、调整定论表、改收尾判据）
- 定期规则健康检查（补充 `rules-weekly-audit.js` 的机检盲区——接线/心跳/篇幅之外的语义冲突）
- 新增能力的准确性、普适性、澄清与授权边界主张审阅

## 新增能力与验证主张审计

1. **拆开主张**：条款完整性、独立情景推演、真实用户问答与跨场景验证分别列证据；静态短语检查、删条款负对照或助手自拟文件操作不能证明模型能正确理解所有请求。证据类型沿用 `verify-before-claim`，不另造等级。
2. **追溯执行链**：从本轮原始记录核对实际输入、使用的提问工具、用户实际答复、批准对象及后续动作；没有真实提问或答复就不能写「澄清功能实测通过」。助手写的 A/B 操作夹具与 C/D 文案推演须分别标注，不能合称真实用户验证。
3. **保留全部阻塞**：用同时缺少目标、凭据和对外口径的反例检查「唯一待确认项」是否遗漏条件；可以优先问一个核心问题，但其余真实阻塞必须保留。明确需求和已答问题不能被重复追问。
4. **审计当前意图**：当前仅优化提示词或只读审阅时，不沿用旧实施授权；有效接续也须核对本轮请求、对象、动作、环境与批次。另用「优化提示词内含删除/部署命令」的反例检查是否误触发执行，不实际执行这些动作。
5. **限制结论强度**：分别写「逻辑合理」「有限场景已验证」「普适性未验证」并列出覆盖范围；发现夸大主张时明确纠正。引用原声明与实际证据，复用下文五要素输出差异。
6. **检查断言是否真的驱动被测入口**：读判据函数体，确认它调用的是被测系统而不是自己刚写进去的夹具；自拟文件操作、静态短语匹配、被别的门槛顺带满足的分支，都只能支撑条款完整性，不能写成"实测通过"。
7. **三档分别输出**：报告里把 ① 审阅建议（未授权执行）② 已获授权的实施范围 ③ 验证缺口（未验证 + 原因）分节列出，不混写。审阅建议不当测试承诺，实施完成不等于普适结论成立。

正例：静态断言通过，只报告条款完整；真实问答记录只支持该输入和环境。反例：用文本匹配通过宣称所有场景都能正确澄清，或把审阅建议视作测试/整改授权。

审阅不自动转为新测试、整改或文件写入；已有记录不足时明确标注缺证，不为补证明力擅自派单、联网认证或运行破坏性反例。

## 家族一致性审计（多载体同主题的五个面）

适用：同一方法论落在多个载体（技能 description/正文、校验器脚本、rules 文件、分享包文档）后，核对它们是否还互相一致。

1. **五面核对**：description 触发词、正文流程、校验器实际判据、对应 rules 条目、分享包内文档，按四层模型逐面对照；一面改了其余面没跟上即记冲突。
2. **代码判据要用夹具验**：校验器/脚本判据构造正例＋负例夹具跑真脚本，不静态读码下结论；重点防校验器假绿（实例：AGENTS 硬约束被「会话规则」泛匹配误命中）。
3. **分级处理吸收检查**：方法更新时逐档（小/中/大）核对处理是否都被吸收，不只在高档补一段就当作全覆盖。
4. **修复后同批同步分享包**：改在生成器真源再重生成重打包，产物侧手改会回灌（见 `generated-artifact-content-audit`）。
5. **输出沿用五要素**：与六维审计相同的原文引用/文件:行/行为影响/改文/扩权标注，分级 P0/P1/P2。

## 六维比对对象

1. **AGENTS.md**：全局纪律（定论表、冲突裁决优先级、操作安全红线）
2. **rules-reminder.js**：每轮注入的提醒文案（UserPromptSubmit/SessionStart）
3. **stop-gate.js**：收尾门禁判据（R1b/R2/R4/R6 等）
4. **rules/*.md**：领域规则文件（delivery-pr/long-task/text-edit-safety 等）
5. **记忆索引**：MEMORY.md 及关键记忆条目（feedback-*/reference-*）
6. **常驻技能 description**：skills/*/SKILL.md 的 frontmatter description

## 执行步骤

### Step 1：六维采集

读取上述六类文件，提取关键约束与判据：
- AGENTS.md 全文（重点：定论表、冲突裁决优先级、操作安全红线、停手检查表）
- `~/.qoder/scripts/rules-reminder.js` 提取每轮注入的提醒文案
- `~/.qoder/scripts/stop-gate.js` 提取收尾判据（R1b/R2/R4/R6 的判定词表）
- `~/.qoder/rules/*.md` 全部领域规则
- `~/.qoder/memory/MEMORY.md` 索引 + 关键记忆条目（feedback-*/reference-*）
- `~/.qoder/skills/*/SKILL.md` 的 description 字段

### Step 2：冲突检测（语义级）

逐对比对，检出以下六类冲突：

1. **同文件内自相矛盾**（P0）：如 AGENTS.md 定论表 vs 交付红线同文件打架
2. **跨文件口径打架**（P1）：如技能 description vs AGENTS.md 定论表
3. **每轮提醒文案 vs 主文件**（P1）：口径漂移（提醒比主文件更严/更宽）
4. **stop-gate 判据 vs AGENTS.md 收尾纪律**（P1）：判据词表不一致
5. **记忆条目 vs 主文件**（P1）：如 gated 写入口径只存在于记忆而主文件歧义
6. **规则文件 vs 机制脚本**（P1）：如 edit-guard 与 text-edit-safety 规则口径漂移

### Step 3：意外确认 vs 有意保障二分类

对每条冲突判定：
- **意外冲突**：无意遗漏/口径漂移 → 列入修复清单
- **有意保障**：给出「有意为之」的证据（如注释/历史决策记录/安全红线） → 列入「保留清单」，不修复

判据：有明确保障证据则保留；意图不明标为待核实，不自动当作可删除的冲突。

### Step 4：分级输出

每条冲突产出**五要素**：
1. **原文引用**（两侧）：直接引用冲突的两段文字
2. **文件:行号**：精确到行（如 `agents.md:145` vs `agents.md:105`）
3. **行为影响**：会导致什么误判/多余确认/漏拦截（如"常规工作多出一次确认"）
4. **具体编辑文本**：直接给出修改后的文案（可复制粘贴）
5. **扩权标注**：是否涉及放宽/加严红线（是 → 需用户授权；否 → 口径统一）

分级标准：
- **P0**：同文件内自相矛盾（最易造成摇摆）
- **P1**：跨文件口径打架（影响面大但需跨文件比对才发现）
- **P2**：措辞歧义可能触发多余确认（字面不矛盾但易误读）

### Step 5：审阅与实施分开

- 只读审阅交付报告即完成；未授权不写文件，包括记忆、队列和备份。
- 用户要求实施时，按已审阅范围备份、修改并验证；明确执行选项可以授权其范围，不重复询问。
- 仅确认方案、取消、沉默不授权写入；宿主要求下一轮人工批准时必须等待。
- 权限不足可申请扩大用户有权批准的任务范围；不得换工具、子代理或新会话绕过平台强制权限。

## 输出格式示例

```markdown
## P0：同文件内自相矛盾（1 处）

**1. 定论表 vs 交付红线：commit 测试强度打架**
- 原文引用：
  - 定论表（agents.md:18）："小步原子提交 ⇄ 提交前必须完整检验 | 验证强度看动作影响面：本地增量＝一条能失败的判据+相关测试；推送/开PR/部署/发布＝完整全绿"
  - 交付红线（agents.md:145）："commit 前相关测试绿"（未分档）
- 文件:行：agents.md:18 vs agents.md:145
- 行为影响：本地增量提交时摇摆——按定论表只需"一条判据+相关测试"，按交付红线字面意思要"完整全绿"
- 具体编辑文本：agents.md:145 改为"commit 前相关测试绿（强度按定论表：本地增量＝一条能失败的判据+相关测试；推送/开PR/部署/发布＝完整全绿）"
- 扩权标注：否（口径统一，不扩权）

## P1：跨文件口径打架（2 处）

**2. ship-clean-pr description vs 定论表**
- 原文引用：
  - ship-clean-pr description："推送前完整检验"（未分档）
  - 定论表（agents.md:18）：已分档
- 文件:行：skills/ship-clean-pr/SKILL.md:description vs agents.md:18
- 行为影响：技能触发时提示"完整检验"，用户可能理解为"每次提交都要完整全绿"
- 具体编辑文本：ship-clean-pr SKILL.md 改为"推送前完整检验（强度按定论表分档）"
- 扩权标注：否

## 有意保障保留清单（未动）

- 操作安全红线（备份、预览命中、凭据保护、核心服务禁动）
- 对外可见/不可逆动作弹窗（推 PR、撤回、force-push）
```

## 验证方式

**功能验证**：
- 用已知冲突作为测试用例（如 AGENTS.md 定论表 vs 交付红线同文件打架）
- 重点验证：同文件自相矛盾能否检出、跨文件口径打架能否检出

**格式验证**：
- 输出报告必含五要素（原文引用/文件:行/行为影响/具体编辑文本/扩权标注）
- P0/P1/P2 分级明确
- 保留清单单独列出

**gated 收尾验证**：
- 审阅未授权实施时，检查零文件写入，包括队列和记忆。
- 以选项提交的明确意图和范围判断授权；推荐标记、浏览高亮不等于批准，平台额外审批仍保留。

## 与既有机制的关系

- **rules-weekly-audit.js**：只做机检（接线/心跳/篇幅），不查语义冲突 → 本技能填补语义级空白
- **merge-inbound-qoder-package**：仅在并入场景末尾含「审阅 AGENTS 与技能」一步 → 本技能可独立调用
- **self-evolution**：方向相反（把反馈沉淀为规则） → 本技能审计既有规则的一致性
