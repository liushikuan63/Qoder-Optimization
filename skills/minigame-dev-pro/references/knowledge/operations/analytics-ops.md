## 1. KPI 定义（口径统一，避免跨文件表述冲突）

| KPI | 定义 | 参考健康区间（需实时验证） |
|-----|------|--------------------------|
| D1 留存 | 首日返回用户 / 新增用户 | 休闲 30–45%；参考非承诺 |
| D7 留存 | 第 7 日返回用户 / 新增用户 | 休闲 12–20%；参考非承诺 |
| DAU / MAU | 日活 / 月活 | 比值 >0.2 为较健康粘性 |
| ARPU | 周期总收入 / 活跃用户数 | 品类差异大，仅作纵向对比 |
| LTV | 用户生命周期预估总收入 | 由 ARPU × 预估留存时长推算 |
| 付费率 | 付费用户 / 活跃用户 | IAA 游戏可极低，IAP 看转化 |
| eCPM | 每千次展示预估收益 | 随广告主市场波动，须平台实时数据 |

> ⚠️ 所有区间均为**行业经验参考**，非承诺值；做任何决策前须用项目自身数据回填验证（见 §4 看板）。
> 与 `references/knowledge/market-data.md` 的品类基准交叉核对，标注来源与时效。

## 2. 隐私优先埋点规范（PIPL 联动，P0）

> 详见 `references/knowledge/compliance/national-law.md`（国家法层 L1）与隐私保护指引 SOP。

1. **告知-同意**：采集任何个人信息前，必须在隐私政策中明示采集项、用途、留存期限，并取得用户同意（最小必要原则）。
2. **最小必要**：仅采集支撑核心功能与合规所需数据；不得超范围采集设备指纹/通讯录等敏感信息。
3. **匿名化 / 聚合**：留存分析用数据须去标识化；用户级明细仅用于必要的反作弊与合规核查。
4. **未成年人**：未成年用户数据采集须更严格，不得用于精准营销推送（联动 anti-addiction-sop.md）。
5. **主体资格**：个人主体小游戏在数据采集与用户画像能力上受平台限制（如不能开通部分企业级数据接口），规划埋点前先用 `iap-eligibility.mjs` 确认主体资格。

### 埋点校验（不与第三方 BI 绑定）

- 埋点事件命名统一（动作_对象_场景），避免同事件多名称（联动 consistency-check 跨文件一致）。
- 关键漏斗（新增→激活→留存→付费）事件必须成对出现（有开始必有结束），缺失事件在 qa-plan 回归项中核查。
- 不采集敏感词/违规内容作为用户标签（联动 sensitive-word-gate）。

## 3. 各平台数据合规（分流，禁止串用）

- **微信**：数据接入走微信开放数据域名 / 平台数据接口；iOS 与 Android 数据口径按平台规则分流（参照 platforms.json 全局对象前缀）。
- **抖音**：按抖音开放平台数据接口与隐私规范；跨端数据须分别存储与告知。
- **个人 vs 企业**：个人主体不可用企业级用户画像/精准营销接口（主体闸门，见 iap-eligibility）。

> 所有平台事实以 `references/data/spec-registry.json` 为准，引用前用 `verify-specs.mjs` 核时效。

## 4. 看板搭建方法论（自托管，无外部依赖）

1. **北极星指标**：每项目选定 1 个核心指标（如 D7 留存或次留），其余为护栏指标。
2. **分层看板**：实时层（DAU/崩溃率）→ 日层（留存/付费）→ 周层（LTV/ARPU 趋势）。
3. **异常告警**：留存下跌 >X%、崩溃率突增、付费率异常 → 触发复盘（联动 execution-protocol 监察巡检）。
4. **数据回填验证**：任何"参考区间"上线后须用真实数据回填，更新项目内基准（不污染本知识文件）。
