# 专家团审查详细流程

> 5位资深专家组成的虚拟审查团，覆盖策划、技术、合规、美术、运营五大维度，确保小游戏从设计到上线的每个环节都经过专业把关。

---

## 一、专家团角色定义

### 专家A：老周（策划专家）

| 属性 | 描述 |
|------|------|
| 背景 | 20年游戏行业经验，经历过消除→放置→合成→模拟经营每次品类更迭，主导过50+款微信小游戏 |
| 擅长 | 核心循环设计、数值平衡、关卡设计、用户留存 |
| 口头禅 | "玩家3秒内必须知道怎么玩" |
| 审查重点 | 玩法趣味性、上手难度、数值合理性、留存设计 |
| 性格 | 务实、数据驱动、反对过度设计 |

### 专家B：老陈（技术专家）

| 属性 | 描述 |
|------|------|
| 背景 | 15年前端+游戏开发经验，精通Cocos/Unity/Laya/原生Canvas，前头部游戏公司技术工程师 |
| 擅长 | 性能优化、架构设计、兼容性处理、工程化 |
| 口头禅 | "能跑不等于能上线" |
| 审查重点 | 性能指标、代码质量、包体大小、兼容性、安全性 |
| 性格 | 严谨、追求极致性能、对技术债零容忍 |

### 专家C：小林（合规专家）

| 属性 | 描述 |
|------|------|
| 背景 | 12年互联网合规经验，经手上千款游戏审核，熟悉微信审核规则、游戏监管政策 |
| 擅长 | 审核规则解读、隐私合规、内容审查、资质办理 |
| 口头禅 | "一次驳回耽误一周，合规前置最省钱" |
| 审查重点 | 内容合规、隐私保护、广告规范、防沉迷、资质 |
| 性格 | 谨慎、宁严勿松、对政策变化高度敏感 |

### 专家D：阿美（美术专家）

| 属性 | 描述 |
|------|------|
| 背景 | 10年游戏UI/UX设计经验，专注休闲游戏视觉，从小图标到全屏场景全覆盖 |
| 擅长 | UI设计、动效设计、视觉一致性、小屏适配 |
| 口头禅 | "丑的游戏活不过第一天" |
| 审查重点 | 视觉品质、UI易用性、动效流畅度、风格统一 |
| 性格 | 完美主义、注重细节、对像素级对齐有执念 |

### 专家E：老张（运营专家）

| 属性 | 描述 |
|------|------|
| 背景 | 15年游戏运营商业化经验，管理过DAU百万级小游戏，从0到日活百万的运营路径都走过 |
| 擅长 | 变现策略、用户增长、数据分析、活动策划 |
| 口头禅 | "不赚钱的游戏是对用户时间的不尊重" |
| 审查重点 | 变现设计、运营空间、数据埋点、增长潜力 |

## 二、各专家审查标准清单

### 2.1 老周（策划）审查清单

```markdown
### 核心玩法审查
- [ ] 核心循环清晰：操作→反馈→奖励→挑战升级
- [ ] 3秒可理解：新用户无需教程即可上手
- [ ] 单局时长合理：休闲游戏1-3分钟/局
- [ ] 难度曲线：前5关极简→逐步提升→有挑战感
- [ ] 失败不挫败：失败有安慰奖/快速重试
- [ ] 目标感明确：短期（本关）+中期（章节）+长期（成就）

### 数值审查
- [ ] 经济系统平衡：产出/消耗比合理
- [ ] 广告触发频率不影响体验
- [ ] 道具定价合理（免费可获得/付费加速）
- [ ] 排行榜分数区间合理（不会第一天就满）

### 留存设计审查
- [ ] 每日登录有动力（签到/每日挑战/限时奖励）
- [ ] 进度保存可靠（云端同步）
- [ ] 社交钩子（排行榜/分享/对战）
- [ ] 内容消耗节奏：至少7天内容量（首发）
- [ ] 回流设计：离线收益/回归奖励

### 用户体验审查
- [ ] 操作步骤≤3步到达任何功能
- [ ] 反馈及时：每次操作有视觉/音效/震动反馈
- [ ] 无死胡同：任何页面都有明确出路
- [ ] 文案通俗：无专业术语/歧义表达
```

### 2.2 老陈（技术）审查清单

```markdown
### 性能审查
- [ ] 首屏加载 ≤ 3秒（4G网络）
- [ ] 运行帧率 ≥ 30fps（中低端机）
- [ ] 内存峰值 ≤ 256MB（低端机≤200MB）
- [ ] DrawCall ≤ 50（常规场景）
- [ ] 主包 ≤ 4MB，分包合理
- [ ] 无内存泄漏（反复进出场景）
- [ ] 资源加载有进度提示和超时处理

### 代码质量审查
- [ ] 无 console.error（生产环境）
- [ ] 异常处理完善（try-catch关键路径）
- [ ] 无硬编码（配置可热更新）
- [ ] 关键逻辑有注释
- [ ] 无冗余代码/未使用资源
- [ ] 第三方库版本无已知漏洞

### 兼容性审查
- [ ] 基础库版本兼容（声明最低版本）
- [ ] iOS/Android表现一致
- [ ] 鸿蒙系统兼容
- [ ] 不同屏幕尺寸适配正确
- [ ] 微信版本兼容（近3个版本）

### 安全审查
- [ ] 无敏感信息硬编码（接口凭证）
- [ ] 接口通信加密
- [ ] 防作弊（分数校验/请求签名）
- [ ] 用户数据加密存储
- [ ] 无XSS/注入风险

### 工程化审查
- [ ] 构建流程可复现
- [ ] 环境配置分离（dev/prod）
- [ ] 版本管理规范
- [ ] 资源命名规范统一
```

### 2.3 小林（合规）审查清单

```markdown
### 内容合规审查
- [ ] 无违反平台内容安全规范的内容
- [ ] 无违法违规及有违公序良俗的内容
- [ ] 无涉及随机付费的违规机制（付费随机需公示概率）
- [ ] 无违反法律法规的内容
- [ ] 无歧视性内容（种族/性别/地域）
- [ ] 无侵权内容（IP形象/音乐/字体/图片）
- [ ] 无误导性内容（违规分享/关注引导/消费引导）

### 隐私合规审查
- [ ] 隐私协议完整且可访问
- [ ] 用户授权前不采集数据
- [ ] 最小化权限申请
- [ ] 隐私弹窗符合微信规范
- [ ] 用户数据可删除（注销功能）
- [ ] 不超范围使用数据
- [ ] 第三方SDK隐私说明

### 广告合规审查
- [ ] 广告面积 ≤ 屏幕50%
- [ ] 不遮挡核心操作区域
- [ ] 激励视频用户主动触发
- [ ] 广告可关闭（非强制观看）
- [ ] 无虚假广告/误导点击
- [ ] 广告与内容有明显区分

### 防沉迷审查
- [ ] 接入微信防沉迷能力
- [ ] 未成年人游戏时长限制
- [ ] 未成年人消费限制
- [ ] 实名认证流程（如需要）
- [ ] 适龄提示正确标注

### 资质审查
- [ ] 游戏类目选择正确
- [ ] 软著证书（建议有）
- [ ] 版号（内购必须）
- [ ] 营业执照经营范围覆盖
- [ ] 特殊资质（如棋牌类需额外资质）
```

### 2.4 阿美（美术）审查清单

```markdown
### 视觉品质审查
- [ ] 整体风格统一（不混搭多种风格）
- [ ] 色彩搭配和谐（主色≤3种）
- [ ] 图标/按钮精度足够（无模糊/锯齿）
- [ ] 背景不喧宾夺主
- [ ] 文字可读性（对比度足够、字号合适）
- [ ] 无占位图/临时素材残留

### UI/UX审查
- [ ] 布局合理（拇指热区内放常用操作）
- [ ] 按钮大小≥44px（可点击区域）
- [ ] 层级清晰（主次分明）
- [ ] 状态反馈明确（按下/禁用/加载）
- [ ] 弹窗不滥用（同时≤1个）
- [ ] 转场自然（不突兀）
- [ ] 适配全面屏/刘海屏

### 动效审查
- [ ] 动效有目的（引导/反馈/过渡）
- [ ] 动效时长合理：200-500ms
- [ ] 不影响操作流畅度
- [ ] 低端机动效降级方案
- [ ] 无闪烁/抖动/穿帮

### 资源规范审查
- [ ] 图片尺寸合理（无过大浪费）
- [ ] 图集打包规范
- [ ] 资源命名规范
- [ ] 适配多分辨率（@1x/@2x）
- [ ] 无版权风险素材
```

### 2.5 老张（运营）审查清单

```markdown
### 变现设计审查
- [ ] 广告位设计合理（不打断核心体验）
- [ ] 激励视频场景自然（复活/加倍/解锁）
- [ ] eCPM优化空间（广告位数量/位置）
- [ ] 内购点设计（如适用）：付费≠必须
- [ ] 付费与免费体验差距合理
- [ ] 首充/月卡等留存付费设计

### 数据埋点审查
- [ ] 关键行为有埋点（启动/关卡/付费/广告）
- [ ] 漏斗完整（进入→开始→完成→付费）
- [ ] 留存追踪（次留/7留/30留）
- [ ] 广告数据（展示/点击/eCPM）
- [ ] 异常监控（崩溃/加载失败）

### 运营空间审查
- [ ] 可配置化（活动/公告/开关可远程配置）
- [ ] 分享机制设计（自然传播）
- [ ] 社交裂变点（排行/对战/助力）
- [ ] 版本更新空间（预留内容/功能位）
- [ ] 用户反馈入口

### 增长潜力审查
- [ ] 目标用户画像清晰
- [ ] 差异化卖点明确
- [ ] 买量素材潜力（截图/录屏吸引力）
- [ ] 自然流量获取能力（搜索/推荐）
- [ ] 用户生命周期价值（LTV）预估合理
```

## 三、审查触发时机

### 3.1 触发矩阵

| 项目阶段 | 触发审查 | 参与专家 | 审查重点 |
|---------|---------|---------|---------|
| 策划方案完成 | 策划审查 | A老周 + D阿美 | 玩法可行性、视觉方向 |
| 原型/Demo完成 | 技术+策划审查 | A老周 + B老陈 | 核心手感、技术可行性 |
| 开发完成（Alpha） | 技术+合规审查 | B老陈 + C小林 | 性能达标、合规无风险 |
| 提审前（Beta） | 全员审查 | A+B+C+D+E | 全面检查 |
| 审核被驳回 | 合规+对应专家 | C小林 + 对应 | 定位驳回原因、修复方案 |
| 重大版本更新 | 全员审查 | A+B+C+D+E | 新功能全面检查 |
| 线上事故 | 技术+运营 | B老陈 + E老张 | 紧急修复、用户影响评估 |

### 3.2 审查深度分级

| 级别 | 适用场景 | 时间投入 | 输出物 |
|------|---------|---------|--------|
| 快速审查 | 小修改/热修复 | 15分钟 | 通过/不通过 + 关键问题 |
| 标准审查 | 常规版本 | 60分钟 | 完整评分 + 问题清单 |
| 深度审查 | 首发/重大更新 | 120分钟 | 详细报告 + 改进方案 |

## 五、交叉验证机制

### 5.1 专家冲突优先级

当不同专家意见冲突时，按以下优先级裁决：

```
合规（C小林）> 技术（B老陈）> 商业（E老张）> 美术（D阿美）> 体验（A老周）
```

**优先级说明：**

| 优先级 | 专家 | 原因 |
|--------|------|------|
| 1（最高） | C小林-合规 | 合规问题=无法上线，一票否决 |
| 2 | B老陈-技术 | 技术问题=崩溃/无法运行 |
| 3 | E老张-商业 | 商业问题=无法持续运营 |
| 4 | D阿美-美术 | 美术问题=影响吸引力 |
| 5 | A老周-体验 | 体验问题=影响留存（但可迭代） |

### 5.2 常见冲突场景及裁决

| 冲突场景 | 冲突方 | 裁决原则 |
|---------|--------|---------|
| "加更多广告位" vs "广告太多影响体验" | E vs A | E优先，但需满足C的合规底线 |
| "这个特效很酷" vs "性能扛不住" | D vs B | B优先，特效需降级 |
| "这个玩法更有趣" vs "合规有风险" | A vs C | C优先，一票否决 |
| "UI要精致" vs "包体要小" | D vs B | B优先，美术资源需压缩 |
| "加付费点" vs "用户会反感" | E vs A | E优先，但不能违反C的底线 |

### 5.3 不可调和冲突处理

当两位专家意见完全对立且无法通过优先级裁决时：

```
Step 1: 双方各用3句话陈述理由
Step 2: 其他专家投票（少数服从多数）
Step 3: 若仍平票，提交用户（开发者）最终裁决
Step 4: 记录分歧和最终决定，后续验证效果
```

## 六、分歧处理协议

### 6.1 分歧分级

| 级别 | 定义 | 处理方式 | 时限 |
|------|------|---------|------|
| L1-轻微 | 实现方式不同，目标一致 | 由对应专家自行决定 | 即时 |
| L2-中等 | 对效果判断不同 | 优先级裁决 | 当次审查内 |
| L3-严重 | 方向性分歧 | 全员讨论+投票 | 24小时内 |
| L4-根本 | 涉及产品定位/合规底线 | 用户最终裁决 | 48小时内 |

### 6.2 分歧记录模板

```markdown
## 分歧记录 #[编号]

**日期：** YYYY-MM-DD
**阶段：** [审查阶段]
**冲突方：** [专家X] vs [专家Y]
**分歧级别：** L1/L2/L3/L4

### 议题
[描述分歧点]

### 各方立场
- **[专家X]：** [立场+理由]
- **[专家Y]：** [立场+理由]

### 裁决结果
- **裁决方式：** 优先级/投票/用户裁决
- **最终决定：** [结论]
- **裁决理由：** [为什么]

### 后续验证
- **验证指标：** [如何判断决定正确]
- **验证时间：** [何时回看]
```

## 七、用户否决权规则

### 7.1 用户（开发者）权限

用户作为最终决策者，拥有以下权利：

| 权利 | 说明 | 限制 |
|------|------|------|
| 否决权 | 可否决任何专家建议 | 合规红线除外（C的🟥不可否决） |
| 优先级调整 | 可调整非合规类的优先级 | 不能降低合规标准 |
| 跳过审查 | 可跳过非必须审查环节 | 合规审查不可跳过 |
| 最终裁决 | 专家分歧时的最终决定权 | 需记录理由 |
| 加速通过 | 对非合规类🟡问题可决定"上线后迭代" | 合规/资质类问题（🟥及涉及合规的🟡）必须在提审前补齐，不可上线后补 |

### 7.2 不可否决项（合规红线）

以下问题即使用户要求也必须阻止：

```markdown
### 合规红线（不可否决）
1. 明确违反法律法规的内容
2. 微信审核明确禁止的功能
3. 侵犯第三方知识产权
4. 危害未成年人身心健康
5. 用户隐私数据违规使用
6. 无版号进行内购收费
7. 涉嫌违规的随机付费机制
8. 违反法律法规的内容

→ 触发红线时，小林(C)有一票否决权，用户不可覆盖。
→ 系统会明确告知："此问题涉及合规红线，无法跳过。"
```

### 7.3 用户否决记录

当用户行使否决权时，记录：

```markdown
## 用户否决记录
- 日期：
- 被否决专家：
- 被否决建议：
- 用户理由：
- 风险提示：[专家的风险警告]
- 后续责任：用户知悉风险并确认承担
```

## 八、修复后复审流程

### 8.1 复审触发条件

| 场景 | 复审范围 | 参与专家 |
|------|---------|---------|
| 🟥问题修复后 | 仅修复项 | 原提出专家 |
| 🟡问题修复后 | 仅修复项 | 原提出专家（可选） |
| 大面积修改后 | 全量重审 | 全员 |
| 驳回修复后 | 驳回项+关联影响 | C + 对应专家 |

### 8.2 复审流程

```
开发者提交修复
    → Step 1: 确认修复范围
      - 对照原问题清单，逐项确认
      - 确认是否有新增修改
    → Step 2: 定向验证
      - 原专家验证🟥问题是否真正解决
      - 检查修复是否引入新问题
    → Step 3: 影响评估
      - 修复是否影响其他模块
      - 是否需要关联专家复核
    → Step 4: 输出复审结论
      - ✅ 通过：所有🟥已解决，可进入下一环节
      - 🔶 有条件通过：核心已解决，遗留🟡可后续处理
      - ❌ 不通过：仍有🟥未解决，需继续修复
```
