# 自进化协议详细文件

> 定义Skill知识库的持续进化机制，确保信息时效性、准确性和实用性。
> 本协议覆盖：进化触发、验证流程、日志管理、记忆管理、版本控制、回滚方案、学习闭环、效果度量。

## 一、进化触发器表

### 触发器定义

| 触发事件 | 触发动作 | 影响范围 | 优先级 | 响应时限 |
|----------|----------|----------|--------|----------|
| 微信平台政策更新 | 更新合规规则库+决策树 | 合规路径、上架检查 | P0 | 24h |
| 微信API/SDK版本更新 | 更新技术选型+开发规范 | 技术选型、开发指导 | P0 | 48h |
| 广告eCPM数据显著变化(>20%) | 更新变现模型+收入预估 | 变现决策树 | P1 | 1周 |
| 新游戏引擎版本发布 | 评估并更新技术推荐 | 技术选型 | P1 | 1周 |
| 用户反馈某建议无效/过时 | 标记待验证→验证→修正 | 对应模块 | P1 | 3天 |
| 用户成功/失败案例积累 | 提炼经验→更新案例库 | 对应模块 | P2 | 2周 |
| 行业报告/数据更新 | 更新市场数据+品类推荐 | 类型选择决策树 | P2 | 2周 |
| 竞品格局重大变化 | 更新蓝海/红海判断 | 类型选择、市场情报 | P2 | 2周 |
| 法律法规修订 | 更新合规要求+模板 | 合规模板、审查标准 | P0 | 48h |
| 审核规则变化(拒审原因新增) | 更新上架检查清单 | 上架就绪度 | P0 | 24h |
| 累计10+用户同类问题 | 提炼FAQ→优化对应模块 | 对应模块 | P3 | 1月 |
| Skill使用数据异常(某模块低使用) | 评估是否需重构/删除 | 对应模块 | P3 | 1月 |

### 触发器执行流程

```
事件发生 → 识别触发器 → 确定影响范围 → 分配优先级 → 
├── P0：立即启动验证流程，24-48h内完成更新
├── P1：1周内完成验证和更新
├── P2：2周内完成，可与日常维护合并
└── P3：纳入月度维护计划
```

## 二、进化验证流程

### 四步验证法

#### Step 1: 来源验证

| 来源类型 | 可信度 | 验证方式 |
|----------|--------|----------|
| 微信官方公告/文档 | 最高 | 直接采信，记录URL和日期 |
| 微信开发者社区官方回复 | 高 | 交叉验证官方文档 |
| 行业媒体/报告 | 中 | 至少2个独立来源交叉验证 |
| 用户反馈 | 中-低 | 需复现/验证，不直接采信 |
| 社区讨论/传闻 | 低 | 仅作参考，需官方确认 |
| AI推测/推断 | 最低 | 必须标注，需实际验证 |

**验证规则：**
- P0级更新：必须有官方来源或2个独立高可信来源
- P1级更新：至少1个高可信来源
- P2级更新：至少1个中可信来源+逻辑自洽
- 任何更新不得仅基于单一低可信来源

#### Step 2: 时效验证

| 检查项 | 标准 | 处理方式 |
|--------|------|----------|
| 信息发布日期 | 是否在有效期内 | 超期标记为"待验证" |
| 是否被后续更新覆盖 | 检查是否有更新版本 | 以最新为准 |
| 政策是否有过渡期 | 确认生效日期 | 标注新旧规则切换时间 |
| 数据是否为最新周期 | 确认数据统计周期 | 标注数据时间范围 |

**时效规则：**
- 政策类信息：以官方最新公告为准，旧版立即标记废弃
- 数据类信息：超过3个月标记"可能过时"，超过6个月标记"需更新"
- 经验类信息：超过12个月标记"待验证"
- 技术类信息：跟随引擎/平台版本，跨大版本时重新验证

#### Step 3: 一致性验证

| 检查维度 | 方法 | 冲突处理 |
|----------|------|----------|
| 内部一致性 | 新信息与现有知识库是否矛盾 | 矛盾时验证两者，取正确者 |
| 跨模块一致性 | 更新是否影响其他模块 | 联动更新所有受影响模块 |
| 与用户已知信息一致性 | 是否与之前给用户的建议矛盾 | 如矛盾，准备修正说明 |
| 逻辑自洽性 | 新信息本身是否逻辑通顺 | 不自洽则拒绝，要求补充 |

#### Step 4: 影响评估

| 评估维度 | 问题 | 输出 |
|----------|------|------|
| 影响面 | 影响多少用户/多少模块？ | 影响范围列表 |
| 紧急度 | 不更新会导致什么后果？ | 风险等级 |
| 兼容性 | 旧版建议是否立即失效？ | 是否需要主动通知 |
| 工作量 | 更新需要修改多少内容？ | 预计工时 |
| 回归风险 | 更新是否可能引入新问题？ | 需要回归测试的范围 |

### 验证通过标准

```
全部通过条件：
✓ 来源可信度达标
✓ 时效在有效期内
✓ 与现有知识无未解决冲突
✓ 影响评估完成
→ 执行更新

任一不通过：
✗ 标记为"待验证"
✗ 记录不通过原因
✗ 设定重新验证时间
✗ 当前仍使用旧版信息（标注可能过时）
```

## 四、记忆管理协议

### 分层架构

| 层级 | 名称 | 内容 | 容量 | 生命周期 |
|------|------|------|------|----------|
| L1 | 核心规则层 | 平台硬性规则、法律要求、技术标准 | 无上限 | 永久（随政策更新） |
| L2 | 经验知识层 | 优秀实践、设计模式、运营策略 | 中 | 12个月（定期验证） |
| L3 | 案例数据层 | 用户案例、市场数据、竞品情报 | 大 | 6个月（数据时效性） |
| L4 | 会话记忆层 | 当前用户上下文、偏好、进度 | 小 | 会话结束清除 |
| L5 | 临时缓存层 | 中间计算、草稿、待验证信息 | 最小 | 24h自动清除 |

### 清理规则

| 触发条件 | 清理动作 | 保留规则 |
|----------|----------|----------|
| 信息超过有效期 | 标记"待验证"→验证→更新或删除 | 验证通过的续期 |
| 新信息覆盖旧信息 | 旧信息标记"已废弃"→30天后删除 | 废弃标记保留30天 |
| 容量达到上限 | 按优先级淘汰：L5→L3→L2 | L1永不清理 |
| 用户主动要求遗忘 | 立即删除指定信息 | 不可恢复 |
| 信息被证伪 | 立即标记"错误"→删除→记录教训 | 教训记入L2 |

### 容量控制

```
各层容量预警：
- L2 经验知识层：超过200条时触发整理（合并相似项）
- L3 案例数据层：超过500条时触发淘汰（按相关性和时效性）
- L4 会话记忆层：单次会话不超过50个关键信息点
- L5 临时缓存层：不超过20条，超出时FIFO淘汰

整理策略：
1. 合并：相似经验合并为一条（保留恰当表述）
2. 抽象：多个案例抽象为一条规则
3. 降级：长期未使用的L2信息降为L3
4. 淘汰：过期+低相关性直接删除
```

## 五、知识库版本控制

### 版本号规则

- 当前版本：v1.0.8（版本号随每次升级递增，与 SKILL.md frontmatter / 脚本 VERSION / CHANGELOG / manifest 五处一致）
- 版本号变更条件：每次可交付升级（含事实纠错、结构整改、功能增强）均递增版本号；五处（SKILL.md `version` / `metadata.version` / 脚本 `VERSION` / 更新日志 / CHANGELOG / manifest）必须一致，不可遗漏
- 每次内容/功能更新，必须在 SKILL.md「更新日志」中同步记录（日期 + 变更清单），保持版本与日志一致

### 版本变更记录

实际变更记录统一维护在 **SKILL.md「更新日志」**（唯一存放位置），此处仅说明记录方式，不重复存放任何版本的实际变更内容：

- 每次内容/功能变更后，按 `### <版本号> (YYYY-MM-DD)` + 变更清单 的格式，追加到 SKILL.md「更新日志」
- 同一版本的多次更新合并记录在该版本的同一条目下，不拆分成多份

### 版本管理规则

1. 版本号随每次内容/功能变更递增（现行 1.0.8，后续按语义化版本递增），禁止声明"版本号保持稳定不递增"
2. 每次内容/功能变更，必须在 SKILL.md「更新日志」同步记录（日期 + 变更清单），不可遗漏
3. 更新前保留当前版本快照，更新后核对 SKILL.md 更新日志与内容一致
4. 涉及合规/数据/规则类更新，更新后必须重新运行 verify-specs.mjs / freshness-check.mjs 核实官方最新规范
5. 回滚时同步回滚 SKILL.md 更新日志中的对应记录

## 六、回滚方案

### 回滚触发条件

| 条件 | 判断标准 | 回滚级别 |
|------|----------|----------|
| 更新后用户反馈明显变差 | 3+用户反馈同类问题 | 模块级回滚 |
| 更新内容与官方最新规则矛盾 | 官方发布相反规则 | 条目级回滚 |
| 更新引入逻辑错误 | 决策树输出明显不合理 | 模块级回滚 |
| 重大更新后全面异常 | 多个模块同时出问题 | 全量回滚 |
| 数据更新被证伪 | 数据来源被否认/撤回 | 条目级回滚 |

### 回滚流程

```
发现问题 → 评估影响 → 确定回滚级别 → 
├── 条目级：恢复单条信息到上一版本
├── 模块级：恢复整个文件到上一版本
└── 全量：恢复到更新前的完整快照

回滚后：
1. 记录回滚日志（原因、范围、时间）
2. 标记被回滚内容为"待重新验证"
3. 通知受影响用户（如适用）
4. 启动根因分析
5. 修复后重新走验证流程
```

### 回滚保护措施

- 每次更新前自动保存当前版本快照
- 快照保留策略：最近10次更新快照 + 每次重大更新前的快照
- 回滚操作本身也需要记录日志
- 连续回滚2次以上触发人工审查（标记为"不稳定模块"）

## 七、学习闭环

### 闭环流程

```
用户A实践 → 结果反馈 → 经验提炼 → 知识入库 → 应用到用户B → 验证有效性
     ↑                                                              |
     └──────────────────────────────────────────────────────────────┘
```

### 详细步骤

#### Step 1: 经验采集

| 采集来源 | 采集内容 | 采集方式 |
|----------|----------|----------|
| 用户A成功上架 | 做了什么、关键决策、耗时 | 结构化提问 |
| 用户A审核被拒 | 拒绝原因、修复过程 | 记录拒绝理由 |
| 用户A运营数据 | DAU/留存/收入/广告数据 | 用户主动分享 |
| 用户A踩坑经历 | 问题描述、解决方案 | 对话中提取 |
| 用户A放弃项目 | 放弃原因、教训 | 退出访谈 |

#### Step 2: 经验提炼

```
原始经验 → 去个性化（去除个人特殊情况）→ 抽象化（提炼通用规律）→ 
结构化（按模块归类）→ 验证（是否符合已知规律）→ 入库

提炼规则：
- 单个案例只能作为"参考"，不能作为"规则"
- 3个以上相似案例才能提炼为"经验规则"
- 经验规则必须标注适用条件和局限性
- 与现有规则矛盾时，走验证流程而非直接覆盖
```

#### Step 3: 知识入库

| 入库层级 | 条件 | 标注 |
|----------|------|------|
| L1核心规则 | 官方明确规定 | 来源+生效日期 |
| L2经验知识 | 3+案例验证的通用规律 | 案例数+适用条件 |
| L3案例数据 | 单个有价值案例 | 时间+背景+结果 |

#### Step 4: 应用到用户B

```
用户B提问 → 匹配相关知识 → 适配用户B的具体情况 → 输出建议 → 
标注"基于N个类似案例的经验" → 跟踪用户B结果 → 反馈闭环
```

#### Step 5: 有效性验证

| 验证指标 | 方法 | 周期 |
|----------|------|------|
| 建议采纳率 | 用户是否按建议执行 | 实时 |
| 建议有效性 | 执行后是否达到预期 | 1-4周 |
| 用户满意度 | 用户反馈评分 | 实时 |
| 复购/复用率 | 用户是否再次使用 | 月度 |

### 闭环质量控制

- 每月统计各模块建议的有效性
- 有效性<60%的知识点触发重新验证
- 连续3次无效的知识条目降级或删除
- 高效知识（有效性>90%）提升优先级

## 八、Skill效果度量指标

### 核心指标体系

| 指标类别 | 具体指标 | 计算方式 | 目标值 | 度量周期 |
|----------|----------|----------|--------|----------|
| **使用量** | 日活调用次数 | 每日触发Skill的对话数 | 持续增长 | 日 |
| **使用量** | 模块使用分布 | 各模块被调用占比 | 均衡(无<5%模块) | 周 |
| **使用量** | 用户留存 | 7日/30日再次使用率 | >30% / >15% | 月 |
| **质量** | 建议采纳率 | 用户按建议执行的比例 | >70% | 月 |
| **质量** | 信息准确率 | 建议被验证正确的比例 | >90% | 月 |
| **质量** | 过时信息率 | 被标记过时的条目占比 | <5% | 月 |
| **效果** | 用户上架成功率 | 使用Skill后成功上架比例 | >80% | 季 |
| **效果** | 审核一次通过率 | 首次提审通过比例 | >75% | 季 |
| **效果** | 用户项目完成率 | 开始→上架的完成率 | >50% | 季 |
| **满意度** | 用户评分 | 用户主动评分均值 | >4.2/5 | 月 |
| **满意度** | 负面反馈率 | 负面评价占比 | <10% | 月 |
| **进化** | 知识更新频率 | 每月更新条目数 | >5条/月 | 月 |
| **进化** | 进化响应时间 | 触发→完成更新的平均时间 | P0<48h, P1<7d | 月 |
| **进化** | 回滚率 | 需要回滚的更新占比 | <5% | 季 |

### 健康度评分规则

```
综合健康度 = 使用量(20%) + 质量(30%) + 效果(25%) + 满意度(15%) + 进化(10%)

各维度评分：
- 10分：远超目标
- 8分：达到目标
- 6分：接近目标(差距<20%)
- 4分：明显不达标(差距20-50%)
- 2分：严重不达标(差距>50%)

健康度预警：
- ≥8：健康，保持
- 6-7.9：关注，需改进
- 4-5.9：警告，需立即行动
- <4：危险，需全面审查
```

## 九、协议执行保障

### 责任分配

| 角色 | 职责 | 执行频率 |
|------|------|----------|
| 触发器监控 | 监控外部变化，识别触发事件 | 持续 |
| 验证执行 | 执行四步验证流程 | 按需 |
| 更新执行 | 修改知识库文件 | 按需 |
| 质量审计 | 检查知识库整体质量 | 月度 |
| 效果度量 | 统计和分析效果指标 | 月度 |
| 回滚决策 | 判断是否需要回滚 | 按需 |

### 例外处理

- 紧急情况下（P0），可先更新后补验证，但必须在48h内补齐
- 验证不通过但用户急需时，可输出"未验证信息"但必须明确标注
- 回滚后如果新版本确实正确（旧版有误），可重新应用但需加强验证

## 十、SOP时效巡检机制

> 目的：SOP（操作手册）是合规路径的"执行依据"，规则一旦变更而 SOP 未同步，会导致用户按过时步骤操作被驳回。
> 本机制确保 8 份 SOP 始终与现行规则一致，杜绝"知识库写了但已失效"的隐患。

### 10.1 巡检对象与元数据规范

每份 SOP 文件头部必须包含以下 4 行元数据（缺一不可）：

```markdown
> 最后更新：YYYY-MM-DD      ← 内容最后一次实质性修改
> 最后核实：YYYY-MM-DD ✓    ← 最后一次确认内容与现行规则一致
> 核实周期：每季度/每半年/每年（依据规则变动频率）
> 下次核实：YYYY-MM-DD      ← 最后核实 + 核实周期，到期触发巡检
```

**"最后更新" vs "最后核实" 的区别（极重要）：**

| 字段 | 含义 | 触发变更 |
|------|------|----------|
| 最后更新 | 内容被实质性修改 | 走完进化验证流程、修改了步骤/材料/周期等 |
| 最后核实 | 确认内容"仍然正确"（未改动） | 巡检时核对官方规则，确认无需修改 |

> 仅核实（确认仍正确）不更新"最后更新"，只更新"最后核实"和"下次核实"。
> 只有实际修改了内容才更新"最后更新"。

### 10.2 巡检对象清单与周期

| SOP 文件 | 核实周期 | 依据（规则变动频率） |
|----------|----------|---------------------|
| icp-filing-sop.md | 每半年 | 管局备案政策中等频率变动 |
| software-copyright-sop.md | 每年 | 版权登记办法稳定 |
| self-review-report-sop.md | 每季度 | 审核规则变化较快 |
| privacy-policy-sop.md | 每季度 | 隐私法规与平台规则变动快 |
| anti-addiction-sop.md | 每季度 | 未成年人保护规则变动快 |
| wechat-certification-sop.md | 每半年 | 平台认证规则中等频率变动 |
| version-number-sop.md | 每年 | 版署政策稳定 |
| content-filing-sop.md | 每半年 | 游戏内容备案规则中等频率变动 |

### 10.3 巡检触发方式

Skill 本身无后台守护进程，巡检通过三种方式触发：

1. **主动巡检（用户/维护者调用）**
   ```bash
   node scripts/sop-timeliness-check.mjs --json
   ```
   扫描全部 SOP，按"下次核实"日期判定状态，输出报告并退出码反映是否有过期项。

2. **被动巡检（加载时触发）**
   当 Skill 加载任一 SOP 前，先解析其"下次核实"日期：
   - 已过期 → 加载时附带警告"该 SOP 已超过核实周期（X天），步骤可能过时，建议核对官方最新规则后再操作"
   - 即将到期（14天内）→ 附带提示"该 SOP 即将到核实期（X天后）"

3. **触发器联动**
   第一节"进化触发器表"中 P0 级事件（微信政策更新/法律法规修订/审核规则变化）发生时，强制触发受影响 SOP 的即时巡检，不受核实周期限制。

### 10.4 巡检流程

```
扫描 SOP 元数据 → 判定状态 → 
├── ok（未到期）           → 记录，无动作
├── due-soon（14天内到期） → 提示维护者安排核实
├── overdue（已过期）      → 标记"待核实"，启动核实流程
└── missing-meta（缺元数据）→ 报错，要求补全

核实流程（overdue 触发）：
1. 逐条对照官方现行规则核对 SOP 步骤/材料/周期/费用
2. 内容仍正确 → 更新"最后核实"为今天，重算"下次核实" → PASS
3. 内容需修改 → 走第二节"四步验证流程" → 修改后更新"最后更新"+"最后核实" → 重算"下次核实"
4. 内容已失效且无替代 → 标记"已废弃"，从 knowledge-filter 索引移除，记录进化日志
```

### 10.5 巡检结果状态定义

| 状态 | 判定条件 | 处理 |
|------|----------|------|
| `ok` | 今天 ≤ 下次核实 − 14天 | 无动作 |
| `due-soon` | 下次核实 − 14天 < 今天 ≤ 下次核实 | 提示维护者 |
| `overdue` | 今天 > 下次核实 | 标记待核实，启动核实流程 |
| `missing-meta` | 缺少任一元数据行 | 报错要求补全（P0） |
| `malformed-date` | 日期格式不合法 | 报错要求修正（P0） |

### 10.6 巡检报告格式

```markdown
# SOP 时效巡检报告 - YYYY-MM-DD

## 概览
- 巡检 SOP 数：8
- 状态分布：ok X / due-soon X / overdue X / missing-meta X
- 整体健康度：X/10（overdue=0 满分，每个 overdue 扣 2 分，missing-meta 直接 0 分）

## 明细
| SOP | 最后更新 | 最后核实 | 下次核实 | 状态 | 剩余天数 |
|-----|----------|----------|----------|------|----------|
| ... | ...      | ...      | ...      | ...  | ...      |

## 待处理项
1. [overdue] xxx-sop.md → 已过期 X 天，需立即核实
2. ...
```

### 10.7 责任与例外

- 巡检结果记入进化日志（第三节格式），操作类型标为"核实"
- 连续 2 次 overdue 的 SOP 升级为 P0，强制走完整进化验证流程
- missing-meta / malformed-date 视为 P0 缺陷，巡检脚本退出码非 0
- 例外：若官方规则正处于过渡期（新旧并行），SOP 可临时标注"过渡期：新旧规则并存，截止 YYYY-MM-DD"，核实时不视为过期
