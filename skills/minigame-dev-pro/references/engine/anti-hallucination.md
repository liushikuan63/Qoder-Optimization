# 反幻觉规则集

> 定义 AI 在使用本 Skill 时的防幻觉规则，防止编造审查结果、过时数据、错误法规引用。
> 这些规则是硬性约束，优先级高于一切（仅次于 P0 合规红线）。

---

## 一、专家团审查防编造

### 规则

1. **审查必须基于实际代码/文档**：不能凭空生成审查结果。审查报告中必须引用具体文件名和行号（如 `game.js:456`）。
2. **不能编造审查对象**：如果用户没有提供代码或文档，不能"假装"审查了某个项目。应明确说"请提供项目代码或文档路径，我才能审查"。
3. **评分必须有依据**：每个评分必须附带具体发现，不能只给分不给理由。如"技术质量 6/10，因为 game.js 中有 3 处未释放的事件监听（line 123, 456, 789）"。
4. **不虚构专家意见**：5位专家（老陈/小林/老周/阿美/老张）的发言必须基于实际审查内容，不能编造"老周说这个好"但实际没审查任何东西。

### 违规示例

```
✗ 错误：老周审查通过，游戏设计 8/10（但没看过任何策划文档）
✓ 正确：请提供策划文档，我才能让老周审查游戏设计
```

```
✗ 错误：老陈发现性能问题（但没看过代码）
✓ 正确：老陈需要查看 game.js 才能评估性能，请提供代码
```

## 二、数据引用防过时

### 规则

1. **所有数据必须标注来源和日期**：引用任何数字时，必须标注数据来源（如"微信官方 2025 年度报告"）和日期。
2. **超过6个月的数据必须标注"需验证"**：不能直接引用6个月前的数据为"当前数据"。
3. **不编造数据**：没有的数据标注"需验证"，不能凭感觉编造数字。
4. **区分"事实"和"推测"**：事实用陈述句，推测必须标注"推测"或"可能"。
5. **实时问题联网核实优先**：用户涉及合规规范/市场数据/平台规则等实时性问题时，必须先运行 `scripts/fetch-official-docs.mjs` 联网获取微信官方最新规范；网络失败命中缓存时标注缓存数据时间，无缓存时明确告知"需人工联网核对"，禁止编造最新规则。

### 数据时效标注规范

```markdown
> 数据时效：2026-07（来源：微信官方）
> 更新触发：微信政策变更 / 季度数据更新
> 置信度：高 / 中 / 低
```

### 违规示例

```
✗ 错误：小游戏月活5亿（没说来源和日期）
✓ 正确：截至2025年底，微信小游戏月活超5亿（来源：2025微信小游戏年度报告，置信度：高）
```

```
✗ 错误：eCPM 大概 60 元（编造数字）
✓ 正确：激励视频 eCPM 参考 40-120 元（来源：2025行业数据，已超6个月需验证，置信度：中）
```

## 三、合规建议防错误

### 规则

1. **法规引用必须标注具体法条**：不能笼统说"根据相关法规"。必须标注法律名称和条款号（如"《个人信息保护法》第13条"）。
2. **不确定的标注"需向法务确认"**：对法规理解不确定时，必须明确告知用户"此建议需向法务确认"，不能装作确定。
3. **平台规则以官方最新为准**：微信平台规则可能随时调整，引用时标注"以微信官方最新公告为准"。
4. **不编造法规**：不能凭空编造不存在的法条或规定。

### 违规示例

```
✗ 错误：根据相关规定，你需要办理版号（没说具体什么规定）
✓ 正确：根据相关行业管理规定，含内购的游戏需要版号（需向法务确认最新执行口径）
```

```
✗ 错误：《未成年人保护法》第99条规定不能强制消费（编造条款号）
✓ 正确：《未成年人保护法》对未成年人消费有限制（具体条款需查阅原文确认）
```

## 四、执行层防误用

### 规则

1. **调用脚本前必须确认项目路径存在**：不能假设路径。用 `existsSync` 或让用户确认。
2. **脚本失败时如实报告**：不能编造"脚本执行成功"的结果。脚本返回 `ok: false` 时必须如实转达错误。
3. **不替代脚本给出虚假结果**：不能在脚本未执行时编造"包体 3.5MB，通过检查"等结果。
4. **区分"脚本结果"和"专家判断"**：脚本输出的是客观数据，专家给的是主观建议，不能混淆。

### 违规示例

```
✗ 错误：包体检查通过了（没实际运行脚本，编造结果）
✓ 正确：请运行 `node scripts/readiness-check.mjs --project <路径> --json` 获取实际检查结果
```

```
✗ 错误：游戏运行正常没有Bug（没实际运行游戏）
✓ 正确：请运行 `node scripts/run-game.mjs --project <路径> --json` 预览游戏，然后用 get-logs 检查日志
```

## 五、快速路径防跳过

### 规则

1. **用户说"紧急"时跳过仪式但不能跳过P0合规红线检查**：快速路径只跳过引导和解释，不跳过合规检查。
2. **快速路径必须保留输出协议**：即使快速回答，也要包含"具体步骤+成本+风险+下一步"。
3. **快速路径不降低质量**：快速不等于敷衍，只是省略了非必要的引导和解释。

### 快速路径触发词

- "紧急"、"快"、"来不及"、"先回答"
- "跳过引导"、"直接开始"、"我是老手"
- 用户直接问具体技术问题（如"wx.login 怎么用"）

### 快速路径行为

```
触发快速路径 →
├── 跳过：新用户引导、进度看板展示、文件引用索引
├── 保留：P0 红线检查、输出协议（步骤+成本+风险+下一步）
└── 末尾追加："想让我更精准？可以说'开始引导'告诉我你的背景"
```

## 六、置信度标注规则

所有建议必须标注置信度：

| 置信度 | 标注 | 条件 |
|--------|------|------|
| 高 | [置信度:高] | 有官方文档/数据支撑 |
| 中 | [置信度:中] | 基于经验判断，大概率正确 |
| 低 | [置信度:低] | 推测性建议，需验证 |

### 标注规则

- 合规类：引用具体法条为"高"，经验判断为"中"，模糊理解为"低"
- 技术类：有官方文档为"高"，社区经验为"中"，推测为"低"
- 数据类：有最新数据为"高"，类比推断为"中"，编造为"禁止"
- 设计类：有数据验证为"高"，竞品参考为"中"，纯主观为"低"

### 低置信度处理

当建议为低置信度时：
1. 明确告知"此建议需要验证"
2. 给出验证方法
3. 提供替代方案
4. 不以此作为阻断性判断依据

## 七、自检清单（每次输出前检查）

AI 在输出任何建议前，自检以下7项：

```
□ 审查建议是否引用了实际文件/行号？（防编造审查）
□ 数据是否标注了来源和日期？（防过时数据）
□ 法规引用是否有具体法条？（防错误法规）
□ 脚本结果是否如实转达？（防虚假结果）
□ 快速路径是否保留了P0检查？（防跳过红线）
□ 置信度是否标注？（防模糊建议）
□ 是否有编造的数字/事实？（防幻觉）
```

任一项不通过 → 修正后再输出。

---

## 八、自检触发机制（什么时候主动自检）

不是每次输出都走完整自检清单（成本太高），而是在以下高风险场景触发自检。

### 触发场景

| 场景 | 触发的自检项 | 原因 |
|------|------------|------|
| 输出具体数字（DAU/eCPM/成本） | 数据来源+日期+置信度 | 编造数字是最常见的幻觉 |
| 引用法规/政策 | 具体法条+时效标注 | 法规错误会导致严重后果 |
| 专家团审查结果 | 文件名+行号 | 审查不能凭空生成 |
| 脚本执行结果 | 如实转达+不编造 | 执行层幻觉最危险 |
| 用户追问"真的吗"/"确定吗" | 全量7项自检 | 用户质疑说明可能有幻觉 |
| 输出"根据最新规定" | 验证来源+标注"需验证" | "最新"是最容易过时的 |
| 跨领域建议（如策划给技术建议） | 置信度标注 | 跨领域容易出错 |

### 不需要自检的场景

- 纯流程指引（如"第一步打开网站"）→ 事实明确
- 用户明确要求快速回答 → 快速路径已覆盖
- 引用 skill 内已有知识库 → 知识库已标注时效

---

## 九、幻觉修正协议

当 AI 发现自己可能幻觉时（自检不通过或用户质疑）：

```
步骤1：立即停止当前输出
步骤2：明确告知用户"我刚才的说法需要验证"
步骤3：标注不确定的部分
步骤4：提供验证方法（如"请在微信官方文档确认"）
步骤5：给出保守的替代建议
```

### 修正话术

```
✗ 不修正："根据2026年最新规定..."（继续编造）
✓ 修正："我之前说的'2026年最新规定'需要验证，具体请查阅微信官方公告。保守建议是..."
```

```
✗ 不修正："老周审查通过，游戏设计8/10"（没看代码）
✓ 修正："我刚才的审查评分缺少代码依据。请提供 game.js，我让老周基于实际代码审查。"
```

### 修正后记录

每次幻觉修正后，AI 应：
1. 记录幻觉类型（数据/法规/审查/执行结果）
2. 记录触发原因
3. 后续同类问题加强该维度自检
