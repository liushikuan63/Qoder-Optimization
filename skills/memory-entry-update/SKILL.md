# 记忆条目更新

## 授权范围

用户明确要求新增、更新或删除特定长期信息，才允许相应写入；修改已有条目、描述和索引也不能省略这一前提。本技能处理已有条目，不代替新增条目的范围确认。
只读审阅不备份、不编辑、不写索引或同步副本；仅返回差异和建议，普通重试与临时纠正不授权记忆写入。

## 为什么要成对改

一条记忆有三个载体，漏一个就会漂移：

1. 记忆正文（`memory/<name>.md`）
2. 正文的 frontmatter `description`（检索与索引用）
3. `MEMORY.md` 的索引行（**不带 frontmatter**，必须单独同步）

## 步骤

1. **Read 两个文件**：正文 + `MEMORY.md`，确认条目已存在、当前措辞与链接。
2. **备份两个载体**（改哪个备哪个）：
   ```bash
   node ~/.qoder/scripts/backup-file.js "<memory 文件>"
   node ~/.qoder/scripts/backup-file.js "<MEMORY.md>"
   ```
   不要用 `cp` 手搓，备份会无裁剪地堆积。
3. **Edit 三处成对改动**：
   - 正文：按锚点插入/替换，保留其他会话内容；
   - frontmatter：`description` 单行，反映新增内容；
   - 索引：`- [标题](file.md) — 一句话钩子`，不超过约 150 字符。
4. **四条可失败验收**：
   - 对照用户要求核对正文含义与 frontmatter 描述，而不只检查关键词存在；
   - 核对索引行的目标文件、名称和摘要与正文一致；
   - Glob 确认没有新增平行条目，备份文件不计作记忆条目；
   - 对照改前内容确认改动仅限获准条目与索引，其他会话内容仍在。
   涉及客户端同步或规则机制时，再运行 `node ~/.qoder/scripts/rules-weekly-audit.js --no-fix` 核对相关项；无关告警不作为本次更新的完成前置，也不授权顺带整改。`[INFO]` 行不是告警。
5. **汇报**：写清改了哪三处、验收命令与结果；提示词层无法程序化验证的部分显式标「未验证 + 原因」。

## 两侧记忆已存在真分叉时

国际版与 CN 版 `MEMORY.md` 可能本来就各有独有条目（真分叉），此时不能要求周检整体 0 告警后收口：

1. 先跑一次 `rules-weekly-audit.js --no-fix` 记录**基线**（哪些告警是既有的）。
2. 只定点修改两侧共同的索引行与同名正文；不复制整份 `MEMORY.md`，不删对方独有条目。
3. 验收改为：正文与索引各只有一条、没有新增平行条目、**未新增告警**；允许周检因既有分叉继续非零。
4. 汇报明确区分“既有红”与“本轮新增红”；本轮新增红必须归零，既有红只报告不改。

## 边界

- 只更新经核验的长期事实；短期进度、排错配方、代码结构不进记忆。
- 按当前记忆规范区分用户级与项目级；不把项目进度写入长期记忆。
- 多客户端先核对真源与获准同步范围；同源只改一次，实体副本只在批准范围内同步，未批准的一侧只做差异检查。
- 删除条目时同步删索引行，避免悬空引用。
