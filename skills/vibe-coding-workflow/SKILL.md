# vibe-coding-workflow

大需求最容易死在两件事上：**在需求没说清时选技术栈**，和**一口气写完再调**。五阶段是给这两件事上锁的。

**每阶段检查准入并给小结**；已获连续实施授权且条件满足时继续。只有用户明确设置的阶段批准才等待，不把质量检查当作逐阶段问询。

## 四层载体（与五阶段对应）

| 层 | 载体 | 对应阶段 |
|---|---|---|
| 宪法：怎么在这个项目干活 | `AGENTS.md`（地图 / 命令 / 禁区 / 按需阅读） | 全程稳定；① 之前就存在 |
| 功能契约：做什么 / 为什么 / 验收 | `spec.md`（窄契约 6 节，只写 what/why） | ① 产出并冻结 |
| 实施计划：怎么做 / 分几步 | `plan.md`（≤60 行）+ `tasks.md` | ② 规划；③ 逐任务 |
| 运行时上下文：此刻知道什么 | 当前任务 + 文件 + 错误 + checkpoint | ③④⑤ 每轮 |

每轮只发当前层：宪法只给路径不重贴，契约只引用 UC 与节号，任务只发一张卡。**需求描述只付一次钱**。
小项目不必四样全上：一页 `AGENTS.md` + 一页窄 `spec.md` + 聊天任务卡即可；字段级契约、完整 UI 四态、全量版本冻结只在跨人 / 长周期 / 高风险时加。

## 五阶段速查

| # | 阶段 | 准入（上一阶段给了什么才开工） | 产出 |
|---|---|---|---|
| ① | **需求澄清** | 用户描述过想做什么 | `spec.md`：谁用 / 什么场景 / 痛点 / 一次典型流程 + **≥3 个异常场景** + **可测试验收标准** |
| ② | **架构** | `spec.md` 已确认 | `plan.md`：到**文件级**的目录结构 + 每文件职责 + 数据流 + 模块接口约定 + **最脆弱 / 最不确定的一处** |
| ③ | **逐模块生成** | 计划已定 | `tasks.md` 每张卡：路径 / 职责 / 依赖与对外接口 + 一段最小验证（至少"能 import + 关键函数能调"） |
| ④ | **调试** | 有具体现象可复现 | 四步法走完的记录（见下）+ 三行总结 |
| ⑤ | **迭代** | 有明确的变更诉求 | 按三种切入点回到对应阶段 |

### ① 需求澄清：**先不碰技术栈**

只谈**谁用 / 什么场景 / 痛点 / 一次典型流程**。此阶段出现 React / MySQL / Redis 这类词就是越级——技术栈是②的事，提前定等于用实现细节掩盖需求没想清。

**技术栈属于计划，不属于澄清**：在②开始时选型并写进 `plan.md`，spec 只写 what/why 与验收。选型写进计划后就冻结，要改先改计划再改代码。

产出里两样不能省：

- **≥3 个异常场景**：网络断了、数据为空、权限不足、并发点了两次……只写正常路径的需求文档等于没写。
- **可测试验收标准**：每条都要能失败。写"非法输入返回 400 且 error.code=INVALID_PARAM"，不写"输入校验完善"。

这些内容直接落进 `spec.md`（§2 不做 / §4 行为约束 / §6 验收），不另起一份需求文档。

### ② 架构：必须点名**最脆弱的一处**

到文件级的目录结构、每文件职责、数据流、模块接口约定。此阶段**不写实现**。产物是 `plan.md`（≤60 行：改动集合 / 首选与回退 / 技术栈 / 验证 / 回滚），不是第二份 spec。目录结构默认放 `plan.md`；高配契约集中时可放 `spec.md §8`，同一事实只出现一次。

**最脆弱 / 最不确定的一处必须写出来**——不写就等于没有风险意识。它通常长这样："订单状态机的并发迁移没有现成方案，先按单机锁实现，多实例部署时会失效。" 这句话是下一阶段排期和验收的依据。

计划获批后，清空规划上下文或开新会话，只带 `AGENTS.md + spec.md + plan.md + tasks.md`——别让几十轮探索历史继续占窗口。

### ③ 逐模块生成：一次只在一个模块的上下文里写

每模块先写清路径 / 职责 / 依赖与对外接口，然后**只在这个模块的上下文里写代码**。跨模块一起写正是长对话漂移的源头。

首次业务工具操作或写入前，按 [skills-router 的项目约定入口](../skills-router/SKILL.md) 形成五维任务约定包；明确规范直接继承，冲突与未知项不自行补绿。配套语言资源、风格、工具、依赖和版本检查进入同一计划；本地、隔离、指定项目、现役范围与自动/分工/人工验证分别选择，不因一个阶段通过自动进入下一授权范围。

**每模块配最小验证**，且要能跑："能 import + 关键函数能调"是底线，不是目标。验证跑不通就不要往下一模块走——那会把调试成本推到后面集中爆发。

验证失败写 `IMPLEMENTATION_LOG.md`（命令 / 退出码 / 最后 30 行 / 最小复现）并停止，不宣布完成。

**输出只给本轮变更文件**：不回显未改动代码、不重复已有内容、不解释设计思路。

### ④ 调试：四步法

1. **完整报错 + 触发操作 + 期望 / 实际**——三样缺一不可。"不行"不是报错信息。
2. **解释原因**：给 1–3 个可能 + 排查顺序，别直接改。
3. **分步修**：一步一验证、逐步反馈，不一次改五个地方。
4. **三行总结**：改了什么 / 为什么 / 还剩什么。

**同一问题连续 3 轮没解决 ⇒ 别在原地硬撑**：先把**现场与已试方案落盘**（改到哪、试过什么、当前判断），再换会话换角度重来。落盘是前提——不落盘就换会话等于把已经排除的路重走一遍。

改 bug 用 **L2 锚点指令**（`文件:函数名` + 行号 + 只改什么 + 不要动什么），不要让它重读整个仓库——那是调试阶段最贵的动作。

### ⑤ 迭代：三种切入点，别一律从头

| 变更类型 | 回哪个阶段 |
|---|---|
| 加新功能 | **①** 需求澄清（这是新需求，不是补丁） |
| 性能 / 体验问题 | **④** 调试（有现象就有得查） |
| 结构混乱、越改越乱 | **②** 架构（说明架构已经撑不住当前需求） |

意图变化时先改 `spec.md`，再同步 `plan.md` / `tasks.md`，不要让代码成为唯一事实。

判断不准时用脚本：

```bash
node ~/.qoder/skills/vibe-coding-workflow/scripts/route-phase.js "改了登录接口后，页面点提交就白屏"
node ~/.qoder/skills/vibe-coding-workflow/scripts/route-phase.js --selftest   # 自测路由表
```

## 与别的技能衔接

- 需求还只有感觉词（"酷 / 极简 / 硬核"）⇒ 先用 `vibecoding-doc` 固化成四层产物（AGENTS / spec / plan / tasks），再进①。
- 要出成套的批次文档（B00 + 批次卡 + 台账）⇒ 按 `rules/vibe-coding.md` 的格式生成，**不另造第二套**。
- 仓库有 `.qoder/repowiki/` ⇒ **先查 wiki 再动手**（技能 `write-repowiki`），别从 grep 冷启动。

## 边界

- **阶段门禁不是仪式**：①的准入没齐就进②，代价会在④集中还回来。
- **小任务不套用**：改一行文案、单点修复走常规流程即可。五阶段是给"新建完整项目 / 跨多模块改造"这类任务的。
- **不发明数字**：业务指标不编造；内部超时等实现参数可选合理默认值并注明，影响验收或安全的未知指标才待确认。
