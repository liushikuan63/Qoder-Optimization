# 目标化执行（设目标 → 逐格推进 → 判据全绿才收）

把"我会努力做完"换成"有一个可判定的目标 + 一组能失败的分格判据"。

## 一、什么时候用

仅用户或系统/开发者明确要求时调用 CreateGoal；已有目标不重复创建。长任务可使用任务清单，不因目录存在任务包或旧队列自动接手实施。先确定本轮授权范围，再从其验收要求提炼判据。

## 二、写目标（唯一硬要求：判据可失败）

用 Goal 机制（`CreateGoal`）设一个目标，**objective 里必须含完成判据**：

- ❌ 坏目标："把分享包更新好"、"优化一下配置" —— 判定不了，等于没有目标。
- ✅ 好目标："出包 5.0：文档计数 = 磁盘实测；四道验证（pack-share-extras / pack-folder / check-share-docs / verify-share-package）全部 exit=0；全量测试 0 失败；本任务适用且获准的接续记录已更新。判据：上述命令的退出码。"

判据写不出 ⇒ 任务没定义清楚，**先澄清**（弹窗问口径），别急着开工。

## 三、逐格推进（稳定性的来源）

1. **拆格**：每格 = **能独立验证**的最小交付单元（一个脚本 + 它的自测、一份文档 + 盘查、一次部署 + 验收）。拆不出判据的格，说明还没拆到位。
2. **每格固定四步**：做 → 验证（判据真跑一遍，拿退出码/截图/计数）→ **落盘**（`/checkpoint` 写进项目根 `.qoder-work-queue.md`）→ 核对目标判据还差什么。
3. **不要攒**：不把"落盘"和"验证"留到收尾。上下文可能先崩；stop-gate 的 R6/R6c 会在收尾时拦下"还有未完成格"和"队列写了但接不了手"。
4. **一次一个目标**：多目标并行 = 哪个都不完整；确实要并行，就分叉会话（`fork_chat_session`）各带一个目标。

### 后台任务：启动 ≠ 完成

后台任务（下载、构建、发布、长测试）要单独登记它和它的后续验证：命令、日志路径、退出码判据、验收步骤。

1. 启动后**等待完成通知，不轮询**；通知到达只算「进程结束了」，不算验收完成。
2. 先核对三项再继续：真实进程退出码、日志里的唯一终态标记（如 `DELIVERY_VERIFIED`）、产物状态。通知里的退出码可能被末尾 `echo` / `tail` 覆盖，不可单独采信。
3. 启动包装必须透传失败退出码（`set -o pipefail` + 显式 `exit $rc`，或让脚本打印终态标记由调用方断言）。
4. 三项一致后再跑依赖步骤与验收，最后关闭任务条目；任一项不符就按失败处理，不进入依赖步骤。
5. 三种不同手段连续失败才停手说明阻塞；只有获得明确续试授权后才继续，不自行增加轮次。

## 四、卡住时怎么办（不允许静默降级）

- 撞到外部条件（凭据 / 进程 / 上游规格 / 用户拍板）：把它写进队列的 `阻塞：<具体条件>`，**保持目标 active**，继续做不依赖它的格子。
- 三种**不同**手段都失败：停手说明阻塞，同时在队列里记「已试过的 3 条路与结论」，避免下一轮重走；重跑同一手段不计入。
- **禁止**：把"跑了命令"当完成、把"看起来对"当完成、把受阻当完成、静默缩小范围（要缩范围就明说并让用户拍板）。

## 五、收尾（只有两种合法形态）

1. **判据全绿** → `UpdateGoal(complete)`，汇报按"已验证（命令 + 退出码）/ 未验证（原因）/ 风险"三段。
2. **被外部条件挡住** → 目标保持 active（或按规则记 blocked），汇报写清是哪一个条件挡住、以及此刻为什么做不了。

**反模式清单**（见到就停手自查）：目标没有判据 · 判据是"我检查过了" · 一格都没落盘就继续下一格 · 用"建议你……"结束（把动作推回给用户）· 中途悄悄改小目标。

## 六、跨会话交接

交付目标、可失败判据、入口和未完成项。仅请求提示词时不自动派发；明确要求代开执行才派发。新会话按本轮授权与目标工具要求决定是否创建目标，不从旧队列推定授权。

## 七、和别的机制怎么配合

| 机制 | 分工 |
|---|---|
| `rules/long-task.md` | 政策层：什么时候该设目标、什么时候该换会话 |
| 项目根 `.qoder-work-queue.md` + `/checkpoint` | 落盘载体：每格做完就更新，四要素齐全 |
| `work-queue-check.js` + stop-gate R6/R6c | 门禁：收尾时拦"还有未完成格""队列接不了手" |
| session-budget | 体积分档：逼近上限时提醒先交接再继续 |
| `verify-before-claim` / `deploy-verifier` 子智能体 | 判据怎么才算"能失败"、验收怎么做真 |
