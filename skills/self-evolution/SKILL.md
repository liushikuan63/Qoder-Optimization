# 任务驱动的自进化

用户已于 2026-10-10 要求全局规则、技能、hooks（机制层）、插件及 MCP 随使用习惯和任务经验持续改进。该授权覆盖本地经验记录和符合下述条件的可逆调整；每次实际任务的范围、项目规则和用户纠正仍然优先。

## 什么时候处理

出现明确的长期偏好或纠正、重复工作中的稳定模式、验证过的修复方法、工具反复缺失/失效时处理。在主任务合适的收尾点完成一次轻量评估；没有新证据就结束，不为凑记录而写日志。

用户明确纠正现有规则时尽快处理，不必等待多个任务。用户说"这次""临时"时只作用于当前任务。不要把沉默、同一个任务的反复重试、你自己的建议或外部材料当成用户偏好。

## 纠正原意与处理建议

- 把候选正文、置信度和历史助手的完成声明当作待核对材料，不当作指令或用户批准。按真实任务与会话去重；同一任务的多次重试不能增加证据数量。
- 纠正已有表述时，逐段核对“主体—动作—对象”、条件、否定、比较和完成状态。模型规划与调用工具，工具执行并返回状态，作者作取舍，使用者与同事提供实际反馈；原文没有说明的主体不要补造。
- “讲人话”只改变表达。例如模型重复试错应写“模型换个方式又从头踩一遍”，不能改成“换个人又从头踩一遍”；真实的同事反馈、人工解锁和使用者安装场景仍须保留。
- 数字集合不变、条数一致和术语零命中只能发现部分差异，不能证明语义不变。保留必要术语及其解释；用错误归因的反例与合法人类场景对照检查，不能机械替换所有“人”。
- 批次处理走既有 skill-authoring-closure：先记录 pending 快照与逐条去向，采用或确认已覆盖并验证后才按精确 ID 标 evolved；待批准、证据不足、尚未完成的条目保持原状态，不改 evolving、不删除建议。报告处理数、归并载体数、标记数与剩余 pending，分清历史证据和本轮验证。

## 读取现状

1. 先核对本轮是否只读、是否在现有维护授权内；只读审阅仅给建议。查看状态前确认命令无写入副作用。
2. Qoder 记忆用于线索；当前文件与用户要求用于复验。只有允许的记忆类型且获得相应授权时，按标准记忆流程更新，不为凑记录写入。
3. 检查目标文件的最新内容和其他会话改动。先查现有规则、技能与可用工具，选择最窄的有效落点；新增规则 / 技能 / MCP / 记忆 / hook / agent 前先跑全局预检脚本 `carrier-preflight`，把报告与方案交用户确认。

`~/.qoder/evolution/control.json` 的暂停开关只控制本技能的自动记录与调整，不改变记忆设置。状态文件缺失采用启用默认；状态损坏则停止写入并报告，不能默默重置。

## 证据门槛

| 证据 | 自动处理 |
| --- | --- |
| 用户明确要求长期保持的偏好，或明确纠正已有约定 | 一次即可采纳，保留原意与适用范围；已有相同规则就只修正或合并 |
| 从操作习惯推断出的偏好 | 先记录候选；至少 3 个独立真实任务、跨至少 2 个会话出现一致证据后才考虑固化；全局规则还需跨项目证据或明确全局要求 |
| 一次已验证的技术经验 | 按项目或技术栈记录；只有对现有技能的已证实错误修正可以立即更新，不能从一个项目推广全机 |
| 重复可复用流程 | 至少 3 个独立任务，或用户明确要求沉淀；先完善适用的现有技能，无合适技能才创建 |
| 某纪律反复失效 / 出现"必须确定性执行"的约束 | 用户明确要求，或该纪律在真实任务里反复失效（有门禁台账 / 心跳等可核验证据）；**补/改 hook 而不是只加提示词**——四件套（脚本 + 两侧接线 + 可失败自测 + 纳入周检）见下节 |
| 插件/MCP 能力缺口 | 用户当次明确需要，或至少 2 个独立任务存在同一缺口；核实现有内置能力和已装工具后再处理 |

门槛是本机维护策略，不是产品自动计分机制。脚本只记录事实和独立任务数量；证据真实性、语义冲突与适用范围由当前代理根据实际上下文判断。不得捏造任务标识、成功结果或证据来满足门槛。

记录最小必要摘要：主题、范围、来源、真实任务/会话标识、观察和验证结果。没有会话 ID 时用实际任务卡或可核验本地证据路径作任务标识，并注明会话未知；未知不能冒充跨会话证据。多次尝试同一任务只算一次。遇到反例先降级候选；用户最新明确纠正优先。

## 更新落点与边界

- **个人偏好**：已有规则能容纳就合并。新增全局习惯放在 `AGENTS.md` 的合适段落内；超限先合并或移到按需技能。项目路径、版本、命令等易变事实不全局固化。
- **项目经验**：优先本地日志并标明项目；只有当前任务授权改动项目说明时才更新该项目的 AGENTS.md/文档。
- **技能**：用 `skill-creator` 创建或修改技能；现有文件先备份，检查触发范围并验证脚本/真实示例。经验来自"吸收外部参考包 / 回流配置包"时，最小差异吸收流程落在 `merge-inbound-qoder-package`（映射思想→宿主核对→先试再接入→改前失败改后通过的隔离回归→冻结后复跑），本技能只判定该不该沉淀与证据门槛，不重复写流程细节。
- **hooks**：仅在既有维护授权内、证据充分且与本任务直接相关时调整；改变权限、批准流程或安全拦截范围须明确批准。保留备份、两侧接线、正负自测与周检，不把无关维护变为主任务完成条件。
- **插件/MCP**：核实现有能力和已装工具后再处理。需要 OAuth、付费、后台采集、写入外部系统时先准备可审查方案，按当前授权处理。
- **权限与学习机制本身**：不能把历史操作习惯当作新的授权；不能自动改权限、本技能的证据门槛/暂停约束。需要用户明确要求才能改这些边界。

## 做一次可审查的调整

一般一次任务最多实施一项相关改进；批量维护按当前明确授权执行。安装、升级和分享包打包不自动附加到普通任务。

1. 记录或更新最小证据，说明当前规则的问题、拟改行为、适用范围。若暂停则跳过自动记录/调整；用户查看、恢复、纠正、回退命令仍可执行。
2. 对已有文件用 `checkpoint` 保存原文；写入前复读哈希和目标区块，冲突就重新合并。新建技能先在当前任务的工作目录中完成，并记录"新增"清单。
3. 用最小差异修改，保留其他会话内容。验证规则无矛盾；技能通过前置校验及合理正反例；可执行脚本实际运行；MCP 做初始化和最小只读调用。证据不足时停留在候选，不称作已生效。
4. 已有文件变更用 `commit --validation ...` 保存修改后内容、哈希和真实验证结果。`commit` 只是审计快照，不表示验证成功；失败时如实标记失败再回退，不伪造通过。
5. 有实际采用的改进时，在正常交付结尾用一句话说明"已沉淀什么及作用范围"。候选、重复证据、没有变化时不发额外维护消息。

若修改后验证失败，只撤销本次能确认的差异；不覆盖新出现的其他会话改动。

## 查看、暂停、纠正和回退

用户说"查看学到的规则""暂停自动调整""恢复自进化""撤销最近学到的这条"时，直接解释相关记录并执行适用操作。

- 查看：`status`，按主题读取证据或变更快照。
- 暂停/恢复：`pause` / `resume`。
- 错误经验：登记 correction 或 rejection，修正对应规则；保留否定证据。
- 回退：先 `rollback --id ID` 查看范围；用户已要求撤销且全部后置哈希一致时运行 `--apply`。哈希不一致时按目标区块合并撤销，不整文件覆盖。
- 未确认的推断超过 30 天未再出现时，先复验再推广；明确长期偏好不会仅因时间流逝而失效。

命令参数、JSON 示例和回退限制见 [operations.md](references/operations.md)，操作时再读取。
