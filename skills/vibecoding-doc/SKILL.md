# Vibecoding 规格与上下文治理（四层分工）

## 先纠正一个方向

**让一份 SPEC.md 承担所有角色，是上一版的根问题**：开头塞满字段、版本、四态，运行时却缺入口命令、当前状态和失败记录；前期过度工程，执行时仍然靠猜。

2026 年的主流做法是拆四层，再按风险决定仪式强度：

| 层 | 只回答一个问题 | 放什么 | 生命周期 | 长度 | 载体 |
|---|---|---|---|---|---|
| **宪法** | 怎么在这个项目干活 | 地图、命令、禁区、红线、验证入口 | 跨功能 / 跨版本 | 半页–两页；根文件 200–500 行 | `AGENTS.md` |
| **功能契约** | 本轮要满足什么 | 目标、明确不做、关键路径、数据/行为约束、验收 | 一个功能 | 1–3 页 | `spec.md` |
| **实施计划** | 怎么做、分几步 | 改动集合、首选/回退、技术栈、验证、回滚、任务分解 | 一次实施周期 | 计划 ≤60 行；任务一卡一验收 | `plan.md` / `tasks.md` |
| **运行时上下文** | 此刻需要知道什么 | 当前文件、错误、进度、按需文档 | 一个 session / turn | 越小越好 | 主上下文 / sub-agent / checkpoint |

**跨会话经验**（`DISCOVERIES.md` / `MEMORY.md`）挂在宪法旁，不是第五层：追加式记录，阶段结束时压缩，不塞进每轮。

降本的主力**不是写更长的提示词**，而是：稳定前缀命中缓存、子 agent 隔离探索、验证闭环减少返工。

## 1. 宪法：AGENTS.md 作为统一入口

**事实（2026-10 核实）**：AGENTS.md 已被 60k+ 开源项目采用，由 Linux Foundation 下的 Agentic AI Foundation 托管；Claude Code 只在工作目录及上层**没有 CLAUDE.md** 时才读 AGENTS.md。所以做法是"一份事实、多工具入口"，而不是复制五份长文：

| 工具 | 默认读什么 | 桥接方式 |
|---|---|---|
| Claude Code | `CLAUDE.md` | 首行写 `@AGENTS.md` 导入，再追加 Claude 专有内容 |
| Copilot | 目录树中**最近**的 `AGENTS.md` / `copilot-instructions.md` | 直接放 AGENTS.md；路径规则用 `applyTo` |
| Gemini CLI | `GEMINI.md` | 把 `context.fileName` 配成 AGENTS.md，或在 GEMINI.md 里 `@AGENTS.md` |
| Cursor | `.cursor/rules/*.mdc` | 保留 AGENTS.md；规则文件写 `globs` / `alwaysApply` |
| Qoder / Codex | 根目录 `AGENTS.md` | 直接用 |

各工具之间的总优先级官方未统一定义，以目标工具文档为准；**不要靠猜**。

### AGENTS.md 骨架（只放地图与红线，不放任务细节）

```markdown
# 项目：订单后台

## 30 秒地图
- 入口：apps/api、apps/web；核心领域：src/domain/orders
- 持久化：packages/db；禁止应用层写原始 SQL

## 命令（每次修改前先跑）
- 安装：pnpm install
- 类型：pnpm typecheck；Lint：pnpm lint
- 测试：pnpm test --filter api；单项：pnpm vitest run -t "<name>"
- 提交前：pnpm lint && pnpm typecheck && pnpm test

## 硬约束 / 禁区
- 不得跳过测试；失败必须修复或记录风险
- 公开 API 变更必须同步类型与契约测试
- 时间统一 UTC，数据库存 timestamptz

## 按需阅读
- 架构与 ADR：docs/adr/README.md
- 测试惯例：docs/testing.md；失败经验：DISCOVERIES.md

## 当前会话规则
- 一次只完成 tasks.md 中的一个任务
- 先读相关文件，再给 3–7 行变更方案；只输出已变更文件的 diff
- 验收失败：写命令、最后 30 行输出、最小复现，停止，不宣布完成
```

**长度纪律**：根文件 200–500 行；单文件 ≤1000 行；单节 ≤80 行；超了就拆文件并留一行"它是什么、何时读"。
**禁忌**：不塞完整日志 / API dump / PDF / 网页；不写"尽量、可能、必要时"这类不可判定的软要求；不写 secrets、个人路径；不把聊天里的临时偏好升格为项目原则；**不写依赖版本矩阵 / 临时决策**——它们变化快，放 `plan.md` 或 ADR。

## 2. 渐进式披露：根文件是地图，不是百科全书

- 根 `AGENTS.md` 只放：项目是什么、启动/验证命令、禁区、子文档索引。
- 架构 → `docs/adr/`；测试惯例 → `docs/testing.md`；失败经验 → `DISCOVERIES.md`；模块细节 → 各 package 的 `AGENTS.md`（工具按目录树取最近文件）。
- **不要**在根文件列 50 个 `@import`——导入数量本身会把"渐进"变回巨提示。
- 容量按"加载频率"定价：每轮都加载的才配放根文件；偶尔用的放子文件，用路径指针引用。

## 3. 风险分级：先决定仪式强度，再决定写多少

| 强度 | 判据 | 产物 | 默认**不做** |
|---|---|---|---|
| **小** | 原型 / 1–2 天 / 单人 | 一页 `AGENTS.md` + 一页窄 `spec.md` + 聊天里的任务卡；任务级 checkpoint | 字段级模型、完整 UI 四态、全量版本冻结、clarify/checklist/analyze 全套、多 agent 编排 |
| **中** | 跨模块 / 多天 / 有对外接口 | 上述 + `plan.md` + `tasks.md`；Plan Mode 只读研究；分层 `AGENTS.md`（子目录）；测试分层；依赖升级隔离；按需加 clarify/analyze | 字段级模型与四态仍需理由 |
| **大** | 跨人 / 长生命周期 / 高风控（认证、支付、迁移、合规） | 上述 + 高配契约（字段级/四态/版本矩阵）+ ADR + 发布前 analyze + 自动评测 / 正式审计 + 多 agent / worktree 协调 + 维护模式（flow-forward / living / flow-back 选一） | —— |

**小项目的高性价比清单**：一页 AGENTS、可执行验收、提交前 typecheck/lint/test、每完成一个可验证任务就提交（按项目授权）、失败先 checkpoint 再回滚。中项目再加 Plan Mode、分层规则、测试分层与依赖升级隔离；大项目才值得上完整 spec-kit / constitution / ADR / 多 agent / 正式审计。

**默认砍掉的三样**（只有满足条件才加，并在 spec 顶部写明理由）：

1. **字段级数据模型**——仅在跨人协作、对外接口、长生命周期、迁移/合规时需要。小项目写语义约束即可（"同一会议室同一时段只能有一条有效预订"），不必先写完整 TS 类型。
2. **完整 UI 四态**——仅在产品上线、多人使用时需要。小原型写"成功态 + 主错误态"就够。
3. **全套依赖版本冻结**——仅在跨人/长周期时需要。小项目保留锁文件 + 禁用危险 API，不必列版本矩阵。

在 `spec.md` 顶部写一行 `强度: 小 / 中 / 大`；写了"大"才校验高配项。

## 3.5 只有感觉、不交给 AI 实施：单篇六节

只要一个原型 / 风格稿，或暂时不交给 AI 写代码时，不要硬凑四层；出一份 `Vibecoding.md` 六节：

1. **🎨 Vibe**：整体感觉、视觉风格、交互体验（落到颜色 / 节奏 / 动效）
2. **🎯 Intent**：一句话说清解决什么问题
3. **📖 User Stories**：2–3 个具体场景
4. **🛠️ Tech Stack Vibe**：偏好栈；无偏好写"AI 自选"
5. **🚫 Constraints**：不做什么、兼容性要求
6. **✨ Success Vibe**：什么样的体验算"就是它"；尽量落成 `- [ ]`

**它不可执行**：一旦要交给 AI 实施，升级成 `spec.md`（六节内容并入 §1 / §4），不要拿氛围稿当验收。

## 4. 功能契约：spec.md 默认只写 6 节（what / why）

| # | 小节 | 必须写到什么程度 |
|---|---|---|
| 1 | 目标与成功画面 | 1 段：项目是什么、谁用、打开后第一屏/第一个结果是什么 |
| 2 | 明确不做 | 逐条列；每写一条，就砍掉模型一大片自由发挥 |
| 3 | 关键路径 | 3–5 条 `UC1: 谁 → 动作 → 结果`，编号化 |
| 4 | 数据与行为约束 | **语义级**：唯一性、状态流转、时间口径、权限、幂等；不是字段清单 |
| 5 | 非功能约束 | 只写真正有要求的：性能底线、错误处理策略、安全、兼容性 |
| 6 | 验收标准 | 可执行命令 + 可勾选清单；至少一条异常路径（空 / 冲突 / 失败 / 权限） |

**高配加档（仅 `强度: 大`）**，追加四节：

```text
## 7. 技术栈与依赖冻结   # 默认放 plan.md；若要契约集中，放这里，同一事实只出现一次
## 8. 目录与文件边界      # 树 + 每文件一句话职责
## 9. 字段级数据模型与接口契约  # TS 类型 / SQL DDL / API 签名 + 错误码
## 10. UI 规格            # 页面 + 区块 + 空/加载/错误/成功四态
```

**边界**：spec 只写 **what / why + 验收**；技术栈、架构、目录、任务分解**默认**归 `plan.md`。高配时把契约集中进 spec 第 7–10 节也可以，但同一事实只出现一次；把 plan 的内容成段塞进 spec，就是回到"一份文档承担四层角色"。

## 5. 计划：plan.md ≤60 行 + tasks.md 一卡一验收

**plan.md**（短生命周期快照，获批即用，不长期维护）：

```markdown
# 计划：<功能>（对应 spec UC1–UC3）
## 改动集合
- 必改（≤5）：path/a.ts、path/b.tsx …
- 可能受影响（≤3）：…
## 方案
- 首选：…；回退：…；两者代价：…
## 技术栈与依赖
- 小项目只列新增依赖；大项目写版本矩阵与禁用项
## 验证
- `pnpm typecheck && pnpm test --filter api`
## 回滚
- `git revert <sha>` / 关开关 / 恢复迁移
## 风险
- 共享状态 / 并发 / 迁移 / 缓存
```

**tasks.md**（300–700 字一张，一次只交一张）：

```markdown
## T-03：创建订单幂等校验
### 只做
- 依据 Idempotency-Key 返回既有 order_id；仅覆盖 POST /orders
### 明确不做
- 不计费、不发通知、不清理旧 key
### 入口
`apps/api/src/orders/create.ts:42-88`
### 验证
- `pnpm --filter api test create-order`
- 同一 key 连续两次调用返回同一 order_id
```

**计划获批后**：清空规划上下文，或开新会话，只带 `AGENTS.md + spec + plan + tasks`。让执行从计划开始，而不是从几十轮探索历史开始。Claude Code 的 `showClearContextOnPlanAccept` 提供了这个选项；其他客户端就手动新开。

计划可以提方案，但**不能未经授权**引入新依赖、换数据库、改鉴权边界或改写公共 API。跨会话状态写 `PROGRESS.md`，决策写 `docs/adr/` 或 `DECISIONS.md`；台账只追加必要条目，阶段结束前压缩。

## 5.5 存量系统改造加档（不另起一套）

判据：对象是已上线系统，有旧菜单 / 旧列表 / 旧流程 / 存量数据，或用户说"原有功能不能缺失"。

在 spec 顶部标 `改造: 存量`，并先建两件（先实测再落笔）：

1. **旧入口清单**：菜单项（key / 顺序 / 选中态推导）、列表列与按钮（读显示条件）、旧表单保存接口、工作流动作、导出字段、新旧动作的状态交叠；逐条标「保留 / 改造 / 下线」，写成 `| 旧功能 | 现状 | 本包怎么处理 | 回归 |`。
2. **设计偏差表**：需求来源与现有实现的差异逐条列出，标「必须让产品知道」的取舍——防执行 AI 按新图重写旧页面。

功能批次后固定一张**兼容回归批**（标题含「兼容回归」），用例取自旧入口清单：菜单可达与选中态、列表按钮只增不减、旧流程走通、终态 / 归档锁定（含绕过前端直调写接口的负例）、DDL 增列后旧 CRUD 不报错、新旧动作不重复不冲突。

**「没删旧代码」不等于「旧功能没坏」**：回归未全绿，只能说"没有主动删除旧代码"。盘点方法与断言模板引用技能 `legacy-entry-compat-regression`，不复制进本包。

需求编号 / Word 自动编号与二手清单冲突时先查权威源：编号域正文无字面量，**不能按表格行或文本行计数反推**（一格多条 bullet 仍只占 1 号），要解包直读 `numbering.xml`；不直接沿用二手清单的编号。

## 6. spec-kit 阶段门：按风险启用，不做全套仪式

| 命令 | 职责 | 何时用 |
|---|---|---|
| `/constitution` | 稳定原则（测试、迁移、禁止直写 SQL…） | 项目已有稳定原则时跳过；有了 AGENTS.md 可并入 |
| `/specify` | 只写用户可见行为与验收（what/why） | **唯一强制**：进入 `/plan` 之前必须有 |
| `/clarify` | 消解实质歧义 | 歧义会改变实现或验收时才用 |
| `/plan` | 技术栈、架构、模块边界 | specify 之后 |
| `/checklist` / `/analyze` | 质量门：契约/计划/任务一致性 | 发布前或高风险时；小需求不跑 |
| `/tasks` | 拆成原子任务，一项一次验证 | 实施前 |
| `/implement` | 一次一个任务 | 逐任务 |
| `/converge` | 代码是否仍符合 spec/plan/tasks | 收尾；缺口补成新任务，**只补任务，不直接改代码/规范** |

只有 `/specify` 是 `/plan` 前的严格前置；把 clarify/checklist/analyze 当每次必跑，就是过度工程。**五阶段流程见 `vibe-coding-workflow`；本节只回答"哪些门是强制的"**，不替代五阶段。

## 7. 上下文工程：稳定前缀 > 更长的提示

**总消耗 ≈ 轮次 × 单轮上下文**。上下文操作只有四个：写入、选择、压缩、隔离。最重要的事实放在开头或结尾，不要埋进长上下文中部（Lost in the Middle）。

### 前缀布局（同一次多轮工作里尽量不改动上半部分）

```text
[稳定]     系统身份 + 项目红线（AGENTS.md）
[稳定]     长期工具定义 / 长期指令
[较慢变化] 当前功能 spec
[快速变化] 当前任务、目标文件、最近错误
[每轮]     最新工具结果（先结论、后证据；>40 行先压缩）
```

- 缓存按**逐字节前缀**匹配：模型、工具 schema、排序、时间戳、trace ID 变了都可能失效。**新增内容追加在尾部，不重写、不重排上半部分**。
- 读取约 0.1×、写入约 1.25×、最小前缀约 1,024 token（OpenAI 口径，2026-10 核实）。
- **缓存降的是费用，不是窗口占用**：缓存前缀仍计入上下文（Anthropic 文档口径；不同产品以实现为准）。所以不能靠"缓存了"就常驻大文档。
- 换功能才换 spec；同一功能内只追加任务与结果。
- **JIT 有取舍**：大型未知代码库保留路径 / 查询，需要时再抓；小型稳定项目用少而稳的 `AGENTS.md` + 2–3 个入口更快，别为"按需"多绕工具回合。

### 压缩与隔离

- **压缩不是复述**：保留当前目标、不可违反约束、已确认决策、未决问题、失败试验、文件锚点、验收结果；丢弃重复 diff、寒暄、工具中间输出、无关探索。压缩前先写结构化 checkpoint。
- **checkpoint 同时记上下文与 git 状态**（当前分支 / 提交 / 回滚点）；只记"想法"不记"现场"，换会话后仍然接不上。
- **子 agent 只用于独立只读 explore**：官方口径是探索可消耗 10K–100K token、返回约 1K–2K 摘要（量级，不是评测均值）。适合：未知代码考古、依赖影响分析、独立模块调研；不适合：共享可变状态、共享类型变更、必须顺序执行的迁移。
- **并行只在任务独立时**：每个 worktree 独立分支 / 端口 / 库 / 命名空间；共享状态、共享类型、顺序迁移不并行——worktree 隔离的是文件系统，不是数据库和端口。
- **模型路由按风险**：规划 / 架构 / 安全审查用强模型，样板 / 小 diff / 日志解析用快模型；这是设计判断，不是已量化定律。
- 工具结果先筛选再进上下文：浏览器/日志/MCP 默认返回大段内容时，先落盘，只回传 `{结论, 证据, 位置}`。

## 8. 验证闭环替代"自述完成"

按顺序跑，退出码进判据：**typecheck → lint → 单元/属性 → 契约/集成 → 端到端（有 UI 时）**。

- 真实输出写入 `IMPLEMENTATION_LOG.md`：命令 / 退出码 / 最后 30 行 / 最小复现 / 时间。
- **失败就停**：不宣布完成、不"顺手重构"、不跳过失败项；修完重跑同一命令。自述完成但验收未过：**回退到上一个 checkpoint**，而不是继续在上面补。
- **交付前按风险分级审查**：UI 文案 / 样式可 diff + 截图快审；认证 / 支付 / 迁移 / 权限 / 并发必须全量测试 + 人工复核。
- 不把"看起来正常""功能正常"当验收；UI 还要真实运行 + 截图比对。
- 汇报区分"已落地并验证"与"未做 / 未验证"。

```markdown
## 2026-10-27 T-03
- `pnpm --filter api test create-order` → exit 1
- 失败：第二次同 key 返回 500（期望 201 + 同 order_id）
- 最小复现：两次 POST /orders，body 相同，头 Idempotency-Key: k-1
- 下一步：查 key 写入时序，不宣布完成
```

## 11. 出稿后必跑校验（结构判据）

```bash
node ~/.qoder/skills/vibecoding-doc/scripts/check-vibecoding-doc.js <AGENTS.md | spec.md | plan.md | tasks.md | 任务包目录 | 单篇 .md>
```

退 `0` 通过 / `1` 有问题 / `2` 用法错误。自动识别：

- **AGENTS.md**：地图 / 命令 / 硬约束 / 按需阅读齐；命令 ≥2 条；根文件 >500 行提示、>1000 行判红；出现明文 secrets 判红；软要求只提示。
- **spec.md（窄契约）**：6 节齐；§2 有清单；§3 有 UC 编号与路径链；§6 有可执行命令与 `- [ ]`。`强度: 大` 或出现第 7–10 节时，加查技术栈版本+禁用项、字段级契约代码块、UI 四态；历史遗留的旧九节 SPEC 仍兼容校验。
- **plan.md**：改动集合 / 方案 / 验证 / 回滚齐；>80 行提示、>120 行判红。
- **tasks.md**：每张卡有 只做 / 明确不做 / 入口 / 验证；单卡 >1500 字提示。
- **四层仓库**：根 `AGENTS.md` + `spec.md`；有 `CLAUDE.md` 时查 `@AGENTS.md` 桥接；`plan.md` / `tasks.md` 存在则一并校验。
- **旧任务包**：`B00` + 总发起指令 + 批次卡连续 + 四件齐 + 台账；包内有 `spec.md` / `plan.md` / `tasks.md` 时一并校验，且 B00 须引用 spec。
- **旧单篇**：六节氛围稿（Vibe / Intent / User Stories / Tech Stack / Constraints / Success）。

它是**结构检查不是质量检查**——"都写了"和"都写对了"是两回事；颗粒度要对照 `references/spec-example.md` 与反面写法逐条过。**判据以脚本实际实现为准**。

### 11.1 判红来源一：围栏注释被当 H1

代码块内的 `# 1) xxx` 会被校验器 `topSections` 当成 H1，把 spec §6 切碎后误判「无可执行命令/无勾选项」。

- **修法**：围栏内注释写成 `#（1）`（半角 `#` 后不接空格），保留 bash 可执行性。
- **错误修法**：改成全角 `＃` 会把命令也弄跑不起来——注释要能跑、标题要别误中，两个约束都要满足。

### 11.2 已有 B00 旧任务包时，新整改包放哪

仓库已有 B00 旧任务包时，新整改包做成**子目录四层**（子目录内自带 `AGENTS.md + spec.md + plan.md + tasks.md + 收口清单.md`）：

- 根目录放 `AGENTS.md` 会把整仓校验切到四层模式、不再检查存量 B0x 卡；
- 根目录放 `spec.md` 会要求改 B00 宪法（并发写风险）。

### 11.3 基线红与台账命名

- **落笔前先跑一次校验取基线**，把「既有红」与本批「新增红」分开汇报——既有红不是你造成的，但要在报告里点名。
- **台账文件名必须匹配 `/收口清单|验收矩阵/`**，否则判「缺台账」；命名前先对齐这条正则。

### 11.4 交付前逐条复核卡内引用

- 交付前逐条 grep 复核卡内引用的 `file:line`（实例：纠出 2 处目录写错）；跨卡引用同一样本时统一文件名。
- 单卡 body 超 1500 字提示时，压缩措辞而不是新增卡（一卡一验收，不是一卡一文件）。

### 11.5 校验目标识别与标题解析（2026-10-29 补）

- **先识别目标类型再跑校验**：分享包仓库、独立任务包、沿用现行约束的方案目录是三套判据。目录自动识别可能把分享包误判成旧任务包并报 4 项「缺失」；命中这种整目录误判时改用**逐文件校验**，不要为了消红去创建无关的 `B00`/规则文件。
- **验证小节只按标题层级匹配**：功能名称或正文里出现「验证」二字不应被当成验证命令段。计划的一级标题若含「验证」，检查器可能把标题正文当小节内容并误报「没有验证命令」——改标题措辞或改走逐文件校验，两者选一，别删真实验收内容。
- **负对照要补齐**：断链、编号重复（任务/验收项）、验收项缺失、代码围栏未闭合，四类各造一个样例确认校验器能判红；判据恒绿等于没校验。

### 11.6 需求扩维后的文档同步

- 从最新用户要求冻结维度和验收 ID，再逐维对齐规格、设计、计划、任务卡与验收矩阵；不要从旧文档计数倒推新范围。
- 每一维同时有任务主责和验证映射，主责唯一，协作任务注明依赖；任务卡正文的验证段也须覆盖，不能只在总表打勾。
- 先区分量具口径过期与文档真实缺项。更新旧计数不代表补齐设计、计划或非国际化维度，不能靠减少需求或改预期消红。
- 负对照分别遗漏一维、指错主责、删除任务验证、伪造完成状态；正常基线仍通过，缺项样本须明确失败。
- 记录状态后重新验证最终文件并冻结内容指纹，防止“验的是旧副本、交的是后来改过的文件”。文档覆盖通过不等于功能已经实现或部署。

## 12. 与相邻载体的边界

- `rules/vibe-coding.md` 仍是**多批次任务包**的权威格式：B00 ≈ 宪法快照，`B0x` ≈ tasks，台账 ≈ IMPLEMENTATION_LOG。新包优先用根 `AGENTS.md + spec + plan + tasks`，旧 B00 包继续有效。
- `vibe-coding-workflow` 管五阶段流程；本技能管"产物怎么分层、每层写多深"。
- `vibecoding-batch-append` 立卡、`vibecoding-batch-execution` 执行；两者都应先读包内 AGENTS/spec/plan/tasks。
- 不另造第二套格式：分层是概念，落到哪个文件按项目现状决定。

## 13. 反面写法（对照）

- ❌ 一份 SPEC.md 同时当宪法、契约、计划和运行日志——前期贵，运行时又缺入口。
- ❌ 小项目上来就冻结全部版本、写字段级模型、补完整四态——边际成本高于收益。
- ❌ 把同一份长文复制到 `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` / `.cursor/rules`——改一处漂四处。
- ❌ 根文件塞完整日志、API dump、50 个 `@import`——渐进式披露变成巨提示。
- ❌ 把 plan 写成第二份 SPEC，或让计划长期维护——计划是短周期快照。
- ❌ 每轮重写系统提示/工具定义/文件顺序——缓存全失效，费用翻倍。
- ❌ 以为缓存命中就不占窗口——省的是钱，不是上下文。
- ❌ 用子 agent 做共享状态修改或顺序迁移——隔离的是噪声，不是一致性。
- ❌ 相信"已完成"自述，不跑 typecheck/lint/test——自述不是执行结果。
- ❌ 为每个小需求跑全套 `/clarify → /checklist → /analyze`——文档速度低于编码速度。
- ❌ 改 bug 时重读全仓、回显所有文件——锚点 + diff 才是低成本路径。
