# 分享包组装、发版与发布后核验

## 适用

- 一个 GitHub 仓库同时承载「源码 + 技能 + 脚本 + 规则文档」，需要改内容、改包名/版本并发布 Release。
- 发布后要证明远端资产与本地构建逐字节一致，而不是只看 CI 绿色。
- 已发布包需要审计，区分静态检查、模拟运行、运行时、产物与原生宿主效果。

产品专用路径、脚本名与门禁清单放 [references/qoder-optimization.md](references/qoder-optimization.md)；主线只写跨包可复用的顺序与判据。

## 0. 先定身份与回滚基线

1. 包身份独立于源码版本：目录名、zip 顶层、`VERSION`、`catalog.package`、manifest 的 `package_name/version`、README、INDEX、技能清单 **八处同值**。组装器必须显式接收 `--name/--version`，禁止从 AGENTS 或上次构建推导。
2. 升版前复制旧目录/旧 zip 作回滚点（或确认 Release 资产可重新下载）；发布态不可变，已发布资产只能发补丁版，不能覆盖。
3. 白名单缩了、脚本改名或技能停用后，旧基线里的文件会继续留在新包：组装后按白名单**剪除**不在名单的文件并打印剪除清单，不靠手工删。

## 1. 组装与改名：先统一身份，再生成派生文件

顺序固定，颠倒会产生旧的计数/旧版本号：

1. 通过仓库已有元数据生成器更新版本与身份描述，并维护 `CHANGELOG`；生成器若需要读取旧版 `VERSION` 才能插入新下载行，先以显式新版本参数预演，不先手改 `VERSION`。本仓库命令见 references。
2. 跑生成器生成 `catalog` / `manifest` / `INDEX` / 技能清单 / 规则文档（它们从目录与 `skills/` 派生）。
3. 若生成器从源文档推导包身份，先改成显式参数，再重跑；否则下一轮身份会被源版本覆盖回去。
4. 统一离线资产与 server 名（旧 server 名会让安装器与守卫 matcher 失配）。
5. 组装后立刻做一次「八处身份一致性」只读断言，别等发布门禁报红。
6. **改名 / 升版时按类扫冲突**，不要逐文件 diff：① 身份漂移（目录 / zip 顶层 / VERSION / catalog / manifest 各说各的）；② 数量漂移（清单写旧数、实际文件数已变）；③ 安装策略自相矛盾（README 一边要求按需安装、一边让全量复制）；④ 新旧双轨（旧技能与新命令/规则同时存在）；⑤ 离线资产版本过期（server 名与哈希仍指旧版）。每类给一条可失败断言，扫完再组装。

## 2. 本地门禁：从已提交的 git 树构建

- **直接检查工作树会把未纳管文件当发行成员**：先冻结要发布的提交，再用构建器（如 `build-release`）从 git 树导出干净目录；输出使用新的仓库外目录，不复用半成品或删除来源/归属未核实的目录。
- 校验器参数按脚本契约传（常见坑：要求 `build.json` 路径却传了目录；要求父目录却传了导出目录本身）。
- 门禁必须能被负对照判红：改坏一条期望值 / 放一个脏文件，确认检查器退出非 0；否则只是恒真脚本。
- README 类硬门禁通常逐项核对：徽章版本、英中各一行版本行、下载 URL 出现次数、计数行、按 description 长度求和的分层字符统计。少一条即红，不要只改 VERSION。

## 3. 发布：tag、CI 与 publish 失败补救

1. 推 main，再打 tag 推 tag；两条 CI 都要核对真实 conclusion 与关键 step，不能只看「有 run」。
2. tag 推送后 publish 报 `invalid remote release metadata` 一类错误，常见真因是「先建草稿再回读」的竞态：草稿在按 tag 查询端点恒 404、列表接口尚未可见。补救用工作流 dispatch 校验并完成既有 tag（见 references），**不要移动或重打 tag**。
3. 已推送的 tag 保持不可变；CI 失败先按既有 tag 查回状态、修复原因，需要源码变更时发新补丁版本，不删除或移动旧 tag。发布说明只列已完成项，未验证项单独写。
4. 远端下载命令在仓库外运行要显式指定仓库（`gh release download -R <owner/repo>`）。
5. 跨平台 CI 上跑安装器预览时，`--dry-run` 不应执行平台安装守卫；预览只提示平台限制，执行阶段仍在动手前拒绝。对应回归用 `--require` 桩覆盖 `process.platform`、`spawnSync` 与网络，断言预览成功且配置不变，同时断言非 dry-run 仍拒绝（见 `verify-before-claim` 的跨平台 dry-run 条）。

## 4. 发布后：远端资产逐字节核验

按证据链顺序，缺一段都不算交付完成：

1. **冻结源码指纹**：记录提交 SHA 与含新增文件的源码树哈希。
2. **从该提交重新构建**：fresh 目录，避免复用旧产物。
3. **敏感扫描 + 分发校验**：确认包内无凭据/内网地址；运行打包前校验器。
4. **隔离消费者探针**：在隔离 HOME/配置目录里用真实入口安装或直调包内脚本；夹具要覆盖短回复、空输出、失败路径。隔离环境会清空认证，远端下载另用官方 CLI 的原有认证，不混用。
5. **下载全部附件**：ZIP、离线包、各自 `.sha256`；逐个与本地构建比 SHA-256。
6. **解压逐字节比对**：对齐顶层目录后 `diff -r`（zip 常带一层包装目录，直接 diff 会整树误报）。
7. **成员数对账**：`zip 成员数 + 独立离线目录文件数 = build.json 清单数`；附件数量与成员集合从构建清单取，不复用历史数字。
8. **消费者验证**：从实际发行包（不是源码目录）安装并走关键路径；CI 绿只证明构建，不证明包内可用。

汇报顺序：源码提交 → CI run/关键 step → Release 链接 → 各附件 SHA-256 → 成员数对账 → 消费者结果 → 未验证项。

## 5. 已发布包审计

- 先冻结不可变基线（版本、文件清单、SHA-256、组件清单），再按组只读审查；不在审计中顺手改包。
- 每条结论标证据层级：`静态`（读文件）/ `模拟`（夹具或纯函数）/ `运行时`（真实进程/请求）/ `产物`（构建出的包与哈希）/ `原生宿主`（真实客户端、真实用户交互）。高层不能由低层替代。
- 修复用差分回归：用 HEAD 副本先复现缺陷（原版必须判红），再在当前修订版验证修复，最后跑全量回归；记录命令、退出码与全树哈希。隔离 HOME 时补齐 `client-root` 等隐式依赖，否则会得到「未复现」的假结果。
- 维护覆盖台账与未验证项；第三方素材/配套的许可不足时只报告，不复制。

### 发布后同步现役

发布不等于现役已更新。同步现役目录前先做三路比对：**现役 live / 旧包 / 新包**。

1. 以现役 live 为基准，逐文件分类：现役较新、包内较新、双方都改、仅一方存在。
2. 备份现役文件；只合并安全修复与已批准内容，保留现役较新内容，不整目录覆盖。
3. 并行会话已改过的文件先甄别归属，不覆盖他人改动。
4. 双端索引重建（两侧各自 `build-skills-index`），再跑现役测试与 `skills-doctor`。
5. 汇报写清“包里已发 / 现役已同步 / 未同步项”。

## 6. 交付判据（可失败）

- [ ] 八处包身份一致，组装器显式版本参数，旧文件已按白名单剪除。
- [ ] 本地门禁从已提交树构建并通过；每条门禁有负对照。
- [ ] main 与 tag 的 CI 关键 step 真实成功；publish 失败按 dispatch 补救，tag 未移动。
- [ ] 远端每个附件与本地产物 SHA-256 相同；解压逐字节 diff 为空；成员数对账成立。
- [ ] 隔离消费者从发行包走通关键路径。
- [ ] 汇报中「已落地并验证」与「未验证/外部阻塞」分开写。
