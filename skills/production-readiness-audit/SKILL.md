# 清单式生产就绪审查

## 适用

用户给来一份长清单（或指着本技能的 [147 条清单](references/checklist.md)），要求「按清单逐项检查我的产品，先别改代码」。目标是产出一份**诚实、完整、可核对**的审查报告：每条要么有证据，要么明说不适用或无法确认。

**固定入口**：vibecoding 四层文档的**最终检测审计阶段**必须调用本技能——`vibecoding-doc` §8.1 与 `vibe-coding-workflow`「交付前：最终检测审计（③④ 完成后必跑）」都把它列为出口判据。理由：typecheck / lint / 单测 / 契约 / e2e 全绿只证明「本轮改动按判据工作」，不证明「整个产品能上生产」。此时被审查对象就是正在开发的产品仓库，报告仍默认落会话工作目录（审查只读），归档进项目 `docs/` 需写入授权。

**不适用**：单个 diff 的评审（`open-code-review-delegate`）、方案/任务卡的反例审查（`counterexample-driven-plan-review`）、验证强度选档与证据纪律（`verify-before-claim`）、云端安全扫描（`security-scan`）。本技能也不负责整改。

## 0. 先核对授权与对象

- 本轮是**只读审阅**还是已授权实施？只读时零写入被审查仓库（报告写到会话工作目录或临时根，不落进被审查仓库）。
- 确认被审查对象的**绝对路径**与产品类型；路径不存在就停下问，不要凭仓库名猜。
- 清单来源：用户给的清单优先；用户没给就用本技能清单，并说明用了哪一份。

## 1. 适用性先判，别为凑清单加功能

先按产品类型过一遍「何时适用」列，把清单裁成三堆：**适用**、**不适用（写理由）**、**待确认**。

- 内部工具不必有 SSO/SAML/SCIM；单体服务不必有多区域；不处理 PHI 就不必 HIPAA。**判不适用是正确结论，不是漏检。**
- 反过来，「不适用」不能当逃生舱：不适用占比超过 60% 时回头核对产品类型判断是否过窄（校验器会给 advisory）。
- **绝不为了满足清单去新增无用功能**——审查的产物是结论，不是功能。

## 2. 逐项取证：四态，各有硬要求

| 结论 | 什么时候用 | 必须给什么 |
| --- | --- | --- |
| `finding` | 适用且确认有问题 | 风险是什么 + 严重度 + 风险类别 + **文件/配置定位** |
| `pass` | 适用且**实测**通过 | 证据路径（测试文件、配置项、实测记录） |
| `not-applicable` | 不适用于本产品 | 为什么不适用（一句话，可核对） |
| `unverified` | 适用但没查到 | 为什么查不到（缺权限/缺环境/缺信息） |

取证纪律：

- **关键词存在 ≠ 行为存在**。看到 `rateLimit` 字样不算限流可用，要真发请求看阈值生效；看到 `csrf` 配置不算 CSRF 防护成立，要带错 token 实测被拒。
- **能实跑就实跑**：登录、越权、重复提交、导入导出、回滚这类项，实测一次比读十遍代码可靠。跑不了就写 `unverified` 并说明缺什么。
- **证据必须落在被审查仓库内且文件真实存在**；行号可选，路径存在性硬性。指向仓库外或不存在的文件＝假证据，校验器判红。
- **不给通用建议**。「建议加强输入校验」不是 finding；「`src/orders/get.ts:42` 只按 id 查询未校验归属，换 id 可读他人订单」才是。
- 严重度按现场证据定，清单里的「缺失默认」只是起点。

## 3. 排序：泄露、资金、中断优先

排序规则是确定的，不靠感觉：严重度降序 → 同级按风险类别（data-leak → money-loss → outage → other）→ 同级按 ID 升序。取前 10 条（不足 10 条就全给）。

前十条每条写四件事：**风险是什么、严重程度、对应文件或配置、建议修法**。其余问题分组列出，不淹没前十。

## 4. 出报告并跑校验器

报告契约见 [report-contract.md](references/report-contract.md)。先写 JSON，再写人读摘要，然后跑：

```bash
node scripts/readiness-report-check.cjs <report.json> --json
```

它判五件事：**清单 ID 全覆盖无漏项**、**finding/pass 必有真实存在的证据**、**不适用与无法确认必有理由**、**未查项不许带严重度**、**前十顺序与规则一致**。退出码 0 才算报告自洽；1 就按违约逐条修报告，**不是改校验器凑绿**。

校验器不判断严重度定得对不对、证据是否真支撑结论——那需要人或独立复核。它只挡住「漏项、无证据结论、给未查项排序、人为调换前十」这四种假绿。

## 5. 交付与边界

- 报告末尾明写：**这是审阅结论，不是实施授权**；整改要用户逐项确认后再做。
- 遇到责任归属问题（谁值班、谁签字、谁对模型负责）查 [human-ownership.md](references/human-ownership.md)。**agent 做过 ≠ 有人负责**。
- 不可逆动作（生产变更、对外发布、破坏性数据操作）一律先给方案与回滚，等明确批准。

## 常见假绿形态

| 形态 | 为什么假 | 改法 |
| --- | --- | --- |
| 清单挑着查，剩下的不提 | 读者以为全查过 | 逐项定性，一条不漏（校验器覆盖判据） |
| 「已检查，未发现问题」无证据 | 无法复核 | 给证据路径，或改 `unverified` |
| 把不适用的项也报成问题 | 制造无用工作量 | 判 `not-applicable` 并写理由 |
| 给没查的项标 critical | 排序被污染 | `unverified` 不带严重度 |
| 前十按「好修程度」排 | 最该修的排后面 | 按严重度+风险类别的确定规则排 |
| 只给通用建议 | 无法落地 | 每条指到文件/配置与具体行为 |
